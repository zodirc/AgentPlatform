# 对齐一次改动

实现、修改和验收以这次任务的决策为准。本 skill 只写对照方法。划分、结构和放弃条件以决策原文为准，不在这里抄一份。

名词、口吻和注释遵循 `agent-writing`。流程图遵循 `.cursor/rules/docs-flow-diagram.mdc`。改了 `services/` 下的代码就补测试，并跑 `scripts/preflight_unit.sh` 里覆盖到的部分，见 `.cursor/rules/ci-unit-sync.mdc`。

决策状态是「提议」时，落地顺序里尚未实现的条目保持未完成。第一条落地之后，整篇仍写「提议」，直到落地顺序全部进入代码。

## 代码按文档实现

代码按照本次任务的决策、执行方案，以及本条改动的客户端与内核方案来写。这些句子是实现范围。

- 函数、表、错误类、锁、默认值、失败后的状态和放弃条件，以这些句子为准。句子里写了的，代码和测试都要覆盖。句子里没有的行为，不加入实现，也不放宽句子里的条件。
- 代码与上述句子不一致时，本条未闭合。已经写进代码的行为，不回写成文档来收口。方案本身要改时，先改决策里的对应句子，再按新句子改代码。
- 决策的「现状」在代码改完后写成代码的真实行为。尚未落地的方案留在决策段。
- 导览正文、详流图、客户端方案里描述同一行为的句子，在同一条改动中改为与决策一致。
- 图、导览和代码上的过期数字，按代码与 `packages/contracts`、导览正文、图的顺序，改正过期的那一层。过期的图和导览不作为改代码的依据。

## 每次检查

不靠上一轮的结论。按落地顺序逐条检查，做到回复里的清单为止。

1. 打开这次任务的决策，按落地顺序写出两份清单，放进这次回复：这次要做的条目，留给后续的条目。后续条目这次不实现，也不写成已经通过。
2. 这次要做的每一条都填下面七格。空格算未通过，不能跳：
   - 代码：路径，以及它实现的决策句子。行为与该句不一致则未闭合。
   - 测试：测试名，以及它断言的失败条件。环境变量、手工步骤、注释都不算。
   - 契约：错误码、schema、夹具。这条不改契约时写「无」。
   - 导览正文或详流图。这条没有用户可见行为时写「无」。图与代码不一致就整张重绘。
   - 决策「现状」里的句子。它必须是代码的真实行为。决策段保持方案，不把实现过程写进去。
   - 客户端文档：客户端与内核方案里被这条改变的句子。没有写「无」。
   - 结论：通过，或未闭合。未闭合要写缺的是哪一格，或哪句决策没有对应实现。
3. 改完一条，从下一条继续。全部改完后把七格再对一遍。代码一改，现状、导览和客户端文档按新行为重写。
4. 七格没有填完，回复里不能出现「已经对齐」或「检查完成」。只报告填了的条目和仍空着的条目。
5. 决策写了放弃或失败条件时，测试必须断言该条件下的结果。只断言成功路径的，该条结论是未闭合。不要放宽断言把它写成通过。

## 闭合

这次清单里的条目，以七格结论「通过」为做完。写「未闭合」是指出还差哪一句，同一轮把这句补进代码和测试，再把结论改成通过。

- 决策里的放弃、失败和零删除，测试要断言这个结果。没有这句测试，不能把结论写成通过。
- 落地顺序写明先做前半、相应测试通过后再做后半的，前半的测试在这一轮通过，后半就在这一轮打开。不要把后半留在回复里。
- 用户明确排除的条目，或决策写明留给后续落地顺序的条目，这一轮不做，也不写成通过。
- 决策点名的外部副本或生产数据不在当前环境时，回复写明缺的是哪一份数据。本地能断言的失败条件仍要补上，不能用缺数据把整条留空。

## 冲突

行为以本次要落地的决策为准，代码按该决策实现。决策「现状」记录改完之后代码的真实行为。导览、图、客户端文档与决策冲突时，改这些文档。代码与决策冲突时，改代码。决策要调整时，先改决策，再改代码。
