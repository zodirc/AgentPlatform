# 模拟线上面试实录

约 50–60 分钟 · Agent 岗 · 个人项目  
对面会抠简历、甩通识、甩场景；压缩/检索往往用**大白话**问（怎么压上下文、召回怎么融），不会先抛项目内部词。答法：**基于…，通过…**，再补例子；内部词当标签用，不当前提。

---

简历三条：

1. 三服务拆分与单 Agentic Loop；故障隔离、按需决策；回合与执行实例一一对应，事件溯源；取消贯穿全程、状态可恢复，长流程可中断可控。  
2. 每步动态上下文组装；按填充率多层智能压缩；按需 RAG 与素材卡写定；长会话更稳，写作成稿引用可核对。  
3. Harness 六面加厚；写作与编码双场景共享内核；子任务委派，完成后摘要回灌。

## 开场

**面试官：**  
简历这个 Agent 平台，一分半钟说定位、场景、怎么跑起来。

**候选人：**  
基于「一个内核、多个场景」：默认写作，另有编码向 Agent。写作通过检索资料、起草改稿、核对引用闭环；Agent 通过更宽工具面改文件、跑命令、等人批。整栈通过 Docker Compose 拉起网关、api、runtime、web 和 Postgres，改好环境变量就能本地跑。

**面试官：**  
模型怎么接？

**候选人：**  
基于第三方 API，通过统一网关做超时、错误分类、出站脱敏。供应商和 key 在设置页写入数据库，下一轮对话生效，不用为换 key 重启容器。回归用 stub，跟日常 live 分开。

## 一、对着简历抠

**面试官：**  
为什么拆 api / runtime / web？

**候选人：**  
基于控制面和执行面分开。  
api 负责登录、创建会话、发消息、点取消/批准，以及把执行过程推到浏览器——它不调模型。  
runtime 负责领走这一轮用户消息，跑「组装上下文 → 调模型 → 调工具」的循环，并把过程写成一条条事件进库。  
web 只根据推过来的数据和汇总视图画界面，不自己猜「现在是不是在检索」。  

runtime 挂了，往往是某一轮跑不动，历史列表通常还能看；api 挂了，发送和推流都会断。拆的是职责，不是三个容器共用一套糊逻辑。

**面试官：**  
你说「推事件」。推的是什么？浏览器看见什么？

**候选人：**  
runtime 往事件表按序追加，api 用 SSE 长连接推给前端。典型包括：  
- **已受理**：点发送后很快一条，页面知道接住了；  
- **正文增量**：助手气泡里字往外蹦；  
- **思考增量**：推理过程直播，刷新可不留，也不进最终成稿汇总；  
- **工具相关**：开始搜索/读文件、结果摘要、写文件要人批；  
- **终态**：完成 / 已取消 / 失败，按钮恢复可发送。  

推的是有类型、有顺序号的事实，不是一个模糊「running」字符串。

**面试官：**  
「事件投影」呢？

**候选人：**  
事件是细流水账，适合直播；刷新和看历史不能让前端自己拼几千条增量。  
投影是异步把流水账收成「回合视图」：当前状态、最新输出摘要、关键工具结果等。  
**事件 = 发生了什么；投影 = 给人看的汇总；SSE = 把新事件推到浏览器。** 投影慢半拍时，执行往往还能继续写事件，用户只是晚一点看见汇总。

**面试官：**  
「按需决策」谁决策？

**候选人：**  
路径上由模型通过 Function Calling 选工具、填参数、写正文。  
事实上由运行时：参数不合 schema 就结构化报错回灌、不执行；写文件/跑命令走审批；命令进沙箱；检索以索引为准。  
不做前置强制意图流水线，避免「改短一点」也空跑。

**面试官：**  
「状态可恢复」——Stop 后能否 Resume 同一个 Run？

**候选人：**  
取消和恢复分开。Stop 后本轮已取消，不 Resume 同一执行实例——半截写盘和半截流说不清；接着干发新一轮，会话上下文还在。  
可恢复指：审批挂起后批准同一轮继续；刷新重连后靠事件和投影对齐界面；进程重启收束遗留 running，不假活、不静默双跑；忙时打字先排队，空闲合并成下一轮。

**面试官：**  
编码场景跟 Cursor？Harness 六面各举一个。

**候选人：**  
共用 while，通过场景配置挂改文件、diff 审批、沙箱命令、跑测试；不是完整 IDE。  
入口可短路少量命令；上下文每步组装，窗紧了再加压；工具白名单+校验+审批；模型网关快失败、未吐字才重试；取消贯串+超时+卡住巡检；Golden 和门禁跟 CI 同契约。加厚不挡首字。

## 二、Agent 通识

**面试官：**  
算不算 ReAct？相对 workflow 怎么补缺点？

**候选人：**  
while + Function Calling，工程上就是 ReAct。简单任务可零工具一轮结束；加能力注册工具。缺点是步数膨胀、乱调工具——用最大步数/预算、schema、晚步收工具表、超时巡检、Golden 补。

---

### 幻觉与乱调工具（细问）

**面试官：**  
幻觉、乱调工具怎么压？再问模型「你确定吗」行不行？

**候选人：**  
不行。再问又多一轮延迟，模型仍可能自信地错，还不适合当可复现门禁。  

分几层讲：  

**1）少给它乱来的机会**  
写作场景和编码场景挂的工具不一样，一开始就不挂全家桶。跑到后面步数多了或窗口紧了，还会把搜索、委派、记忆从**本步工具表**拿掉，减少空转。  

**2）参数入口先卡死**  
tool_call 先过 JSON Schema：缺字段、类型错 → 结构化错误写回对话，**不执行**副作用。模型可以改参再调。  

**3）副作用晚绑定**  
写文件、跑命令要人批；路径必须落在当前作品目录；命令能进 OS 沙箱时限制可写面。  

**4）写作幻觉：引用两条线**  
- 本轮搜到的 id 进**证据账本**；稿子里写了账本没有的引用 → 标未核验。  
- 导出/核查时可扫磁盘：引用锚点在不在文件里，可警告或拦住。  
两样都不调模型，也都不能证明「史学正确」，但能标脏、能挡明显瞎编锚点。  

**5）乱调工具的真实坑（编码侧）**  
用户说「优化某个 HTML」——意图合法，但轨迹可能长时间用 shell 的 head/sed 翻源码，很少落到可审查的小改动；或者以为 propose 补丁就已经改盘了，其实只是入队待批。  
对应约束：读文件走专用工具，结果里写清「读完没有、从哪续、共几行」；禁止把 shell 当翻书器；改盘主路径用「精确旧片段 → 新片段」的编辑；软提示不够时，同一轮内对同一文件重复灌大段内容直接硬拒。  
/
总结：缩小动作空间 + 确定性门 + 可核对痕迹；不靠再问模型。

**面试官：**  
假参数——字段都对，但路径指到别的目录，或搜了个不相干的词？

**候选人：**  
schema 只拦形状。  
路径穿越靠规范化后必须仍在当前世界根；exec 另有沙箱，防止「cwd 在工作区但重定向写出界」。  
搜了不相干的词：运行时拦不住「语义选错」，靠工具描述写清何时用、证据与引用标脏、晚步少挂搜索，减少空搜。三层分开：形状、副作用边界、语义。

### 记忆：短期 / 长期怎么记

**面试官：**  
记忆一般分短期和长期，你们怎么记？怎么进模型窗口？

**候选人：**  
先分层，再讲记法和进窗。  

**短期（跟这一轮、这一会话绑定）**  
- **本轮**：用户这句、模型回复、本轮工具结果——就在 messages 里，工具结果过长会截断，保速。  
- **会话内多轮**：完整对话轨迹会落库；送给模型时不是永远全文，窗口紧了会收短旧工具回传、裁更老轮次，必要时变成一段会话摘要 + 最近原文。未完成项也可以带在会话侧，提醒下一轮接着干。  
- **磁盘上的书稿/文件**：算「比窗口更稳的短期～中期真相」。窗口里往往只放路径指针，需要再 read；换会话也不拆书。  

**长期（跨会话仍想留住的）**  
两类，通道分开：  

1. **资料/事实**：进资料库，走检索工具按需召回，不预灌进 system。  
2. **偏好/约定**（文风、口吻、「以后短句」）：走独立的记忆仓，通过「写入记忆 / 召回记忆」一对工具；模型决定何时写、何时调。文风素材卡可以钉在系统侧当静态规则，**故意不进 RAG**，避免风格句被搜出来假命中。  

**怎么「记录」**  
- 短期对话：随 Turn/会话持久化事件与消息。  
- 长期偏好：模型调写入工具时，写入记忆命名空间（和资料索引分开）。  
- 长期资料：用户导入/变更资料 → 旁路切块建索引，不是写进 messages。  

**怎么进窗**  
默认不盲灌。读文件 ≠ 自动召回偏好；搜资料 ≠ 自动带记忆。用户说「记得上次文风」时，最多加一行轻提示「可以考虑调记忆召回」，不把记忆正文直接塞进 system。每轮自动召回会占窗、拖首字、记错了还难查。

**面试官：**  
静态长期和动态长期有什么区别？

**候选人：**  
静态偏规则：人设、硬约束、钉选的文风卡，优先放稳定前缀。  
动态偏滚动：会话摘要、未完成项、记忆召回结果，随任务变，可截断、可按窗口丢。  
失败模式也不一样：静态是规则冲突、钉太多挤窗；动态是摘要丢细节、旧未完成项过时。

### 其它通识

**面试官：**  
多 Agent？委派？

**候选人：**  
主形态单 Agent 加工具。长探索才委派：传任务说明和文件路径，不传父对话全文；回来只摘要。不上群聊总线，不每轮强制评审模型。

**面试官：**  
怎么评好坏？速率和效果打架？

**候选人：**  
Golden 做行为回归；门禁和 CI 同契约；评测台是切片，跳过≠失败。  
热路径站速率：先回受理；首字前不加同步裁判；建索引、打分旁路。正确性靠 schema、证据标记、离线评测。

**面试官：**  
取消和审批屏上差别？

**候选人：**  
取消：字马上停，终态已取消，可发新轮；不能显示任务失败。  
审批：等人批写文件/命令，批准后同一轮继续；等人批不是停止。

## 三、场景题

**面试官：**  
「根据资料写一段出场并带引用」——从发送到出字。

**候选人：**  
发消息 → api 建轮并很快推「已受理」→ runtime 组装并调模型 → 若搜索则只查已有索引，短摘录+id 进工具结果和证据账本 → 正文增量推到气泡 → 结束时投影成完成态。  
索引滞后可用关键词兜底或提示滞后，交互继续；禁止在这次搜索里同步全量建索引。

**面试官：**  
资料很多怎么办？

**候选人：**  
交互面只读索引；索引面资料变更后异步切块嵌入。查询时不建索引。个人世界检索隔离已做；企业万档运维不是本期。

**面试官：**  
长思考点 Stop，又打了下一条？

**候选人：**  
界面冻渲染，SSE 仍听「已取消」；执行面关掉模型连接。下一条进队列，不塞进当前 messages，空闲后合并成新轮。定时器绑旧 turn id，防误伤新轮。

**面试官：**  
审批连点两次？

**候选人：**  
服务端抢占待批 + 请求幂等号；建轮冲突回读已有回合。

## 四、上下文压缩（对方常用大白话问）

**面试官：**  
长对话上下文会爆。你们怎么做上下文压缩？先别甩术语，说策略。

**候选人：**  
分两档，顺序很重要。  

**第一档：平时每次组装都做的「打扫」**  
工具返回动辄很长，历史里会堆很多「读文件/搜索」的旧正文。组装时：单条过长先截断；很早以前、已经用过的成串工具回传收短，给最近对话和当前工具结果留位置。这档不要求窗口已经满，目的是别让垃圾先把箱子塞满。  

**第二档：真的快满了再升级**  
估算「这次要送给模型的量」占「窗口还能用的量」的比例。大概到八成、九成、九成五，损失逐步加大：收得更狠 → 丢掉更旧的消息组 → 最后才用一段**会话摘要**代替大段旧对话。  
摘要默认是**旧摘要叠加上新发生的片段**，不是每一轮、也不是第十一轮把前十一轮全文重新总结一遍。用户主动点压缩，才可以走更重的全量。  

丢掉的优先是还能再 read、再 search 回来的；用户原话意图、最近几轮、文件路径尽量留。原始对话在库里另有保存，供回放，**默认不整段再塞回模型**。  

（若对方追问内部叫法：日常收短旧工具回传有时叫微折叠；占比叫填充率；最后一档才是摘要。）

**面试官：**  
压缩过程可观测吗？怎么知道压了什么？

**候选人：**  
可观测分几层：  
- **组装耗时、是否触发了哪一档压缩**，运行时指标/日志能看，避免「满窗同步摘要」把首字拖死。  
- **事件与回合视图**：用户侧仍能看到本轮做了哪些工具、最终输出；压缩主要改的是**下一轮送给模型的窗口**，不是把用户历史 UI 偷偷删光。  
- **原始会话仍在库里**，坏摘要可以对照原件重建，不是压完就蒸发。  
- 内部评测/门禁会覆盖长会话相关行为；体验上也会看是否越聊越钝、是否丢了关键约定。  

不会做到「每一次折叠的每个字符都在前台滚动播放」，但策略触发和结果侧可查。

**面试官：**  
压缩质量怎么评判？怎么知道摘要没把关键信息弄丢？

**候选人：**  
没有单一分数能宣布「摘要完美」，用组合办法：  

1. **行为回归**：压缩后仍应能完成关键 Golden（比如还找得到约定路径、还能按资料引用写），而不是只测「窗口变小了」。  
2. **可重建**：原件还在，摘要质量差可以重做；默认增量合并也是为了少做信息衰减的二次煮。  
3. **损失顺序固定**：先丢可再取回的观测，后动意图和热区——质量问题优先表现在「工具噪声是否清掉」而不是「用户原话先没了」。  
4. **体感与旁路信号**：是否反复追问已说过的约束、是否无意义重搜重读；结合延迟，避免为了压窗同步上大模型摘要。  
5. **明确不做的**：不在热路径每轮雇一个裁判模型给摘要打分——慢、不可复现、和速率冲突。  

质量目标是「窗仍是作业面、关键任务能续」，不是「摘要读起来像一篇漂亮作文」。

## 五、检索细节

**面试官：**  
写作这边检索具体怎么做？BM25 和向量是怎么一起用的？

**候选人：**  
先说索引里存的是什么，再说查询怎么糅合。

**召回的对象不是整篇文档，而是「块」**。资料变更后在后台把 Markdown 按标题切成节，太长再滑窗切成多段；每一块带：块 id、所属文件路径、一小段正文（必要时标题也在文本里）、以及向量。文风素材卡不进这套索引。用户搜索时，模型拿到的也不是全文，而是若干**短摘录 + 引用 id**；要通读再调读文件。

查询时两路**并行、各查各的**，不是先 BM25 再向量串着跑：

1. **BM25 路**：查询句分词，在块正文（含标题线索）上打词法分，取出 Top-N 个块。擅长专名、编号、原文措辞对得上。  
2. **向量路**：查询句嵌成向量，在块向量里找近邻 Top-N。擅长换说法、同义改写。  

两路各自得到一份「有序的块列表」。接下来要合成一份给后面用的候选——这里**不把 BM25 分和向量分加权相加**。量纲不同，权重换库就失效。  

糅合用 **RRF（按名次融合）**：每个块看它在 BM25 路排第几、在向量路排第几，用「权重 / (k + 名次)」这类倒数贡献加总；k 常见约 60，避免「只在一路排第一」的块一家独大。同一块两路都靠前，分数叠上去，更容易胜出；只出现在一路，也可以进候选。一路空了就只用另一路。  

RRF 排完后，会得到一堆按融合分排好的**候选块**——我习惯把这一步的结果叫**召回池**：比最终塞给模型的条数更宽（比如先留二十来条），目的是先求别漏。池子里每一项本质是：**块 id + 路径线索 + 短摘录正文 + 融合后的排序位置**（对外展示分一般是 RRF 分，不再假装是原始 BM25 或原始余弦）。

池子还要再收窄：先在小池内做一轮**词法微调排序**（下面展开），再截到工具 limit（比如 10 条）写入 tool 结果进模型窗，引用 id 同时进本轮证据账本。

整条热路径：**两路召回 → RRF 合成宽候选 → 小池词法再调序 → 截断进窗**。建索引不发生在用户这次搜索里。

**面试官：**  
你刚才说的「词法再调序」和 RRF 是一回事吗？有人说的便宜重排是指什么？

**候选人：**  
**不是一回事，前后两步。**  

- **RRF**：解决「两路分数没法加」——输入是**两份**排序列表，输出是**一份**融合后的宽候选。它是融合算法。  
- **词法重排（我说的便宜重排）**：输入已经是**一份不大的候选池**，不再回全库搜。只在这二三十条里，看查询词和标题/摘录重叠、短语是否完整出现、标题是否命中等，给当前分做一点**可解释的小加成**，再排一次序。纯 CPU、毫秒级，不加载大模型。  

它解决的是融合之后的局部问题：比如专名刚好在标题里的块，融完后还可以再抬一抬。  
交叉编码器那种「查询和候选一对一打分」更准但更贵，默认关；那才是贵重排。所以「便宜重排」= 小池内词法微调，**≠ RRF**。

**面试官：**  
那召回依据到底是什么？池子里为什么是这些内容？

**候选人：**  
依据分两层：  

**索引时（决定库里有什么）**  
依据文档结构切块：标题节优先，保证一块尽量是一个可引用话题；过长再滑窗并留重叠，避免人名卡在两块接缝。嵌向量时除正文外会拼路径线索，减少「同名不同类」挤成一团。大宽表在送去嵌入的文本里可换成短指针，磁盘原文不动。  

**查询时（决定池子进谁）**  
依据用户这次查询句：BM25 按词法相关取 Top-N 块，向量按语义近邻取 Top-N 块，RRF 按两路名次共识合成宽池。权限上还要硬过滤，只能看见当前世界允许的资料，别人的私有档进不了池。  

所以池子里不是「文档标题列表」，也不是「模型胡编的句子」，而是**索引里真实存在的文本块的候选集合**；进窗时再变成短摘录 + id 给模型用。

**面试官：**  
检索可观测吗？质量怎么评？

**候选人：**  
前台能看到本轮发生了检索。内部可以按回合对照：融合后的宽候选、词法调序后的顺序、最终进窗的几条——用来区分是「根本没召到」「融进池了但被截掉」「进窗了但模型没用」。  
质量靠带资料的回归用例：该搜到的块是否出现、引用是否进证据账本。不在每次用户搜索后同步再跑大模型当法官。索引滞后允许降级继续聊，但要能发现，而不是假成功。

**面试官：**  
引用「可核对」？

**候选人：**  
证据账本：这轮检索有没有返回这个 id。  
磁盘扫描：锚点在不在文件里。  
都不是史学鉴定。跑完不等于写对。

**面试官：**  
工具太多 token 爆？

**候选人：**  
场景少挂 → Plan 再收 → 晚步拿掉搜/委派/记忆 → 描述写清何时用，前缀稳定利缓存。不加热路径路由小模型。

## 收束

**面试官：**  
一个判断，一个边界。

**候选人：**  
判断：单 loop；意图在模型，事实在运行时；短长期记忆分仓按需进窗；上下文先打扫再按水位加压；检索两路融名次不融分数。  
边界：不对标 Cursor 全功能；无 Org/分享；取消后不 Resume 同一 Run；压缩/检索质量靠回归与可观测，不靠热路径裁判模型。

**面试官：**  
好，今天到这里。

**候选人：**  
谢谢。
