组窗阶梯：卫生与填充率加压

送给模型的不是 Session 全文，也不是磁盘稿。每步 assemble_async 产出这一次请求的窗。通道分离：系统提示求稳定（利于 prefix cache）；tools[] 单独一份且默认不改字节；作品规矩 / 焦点 / 计划走 volatile_context（易变垫底，不焊进 system）；真正被压缩的是对话历史。

  • ◆ 要点 设计取舍：漏了会把 128k 当常驻 RAM、在首 token 前再付一次摘要模型、或改 tools[] 字节打掉缓存

预算怎么算

context_window_tokens = 128 000
output_reserve_tokens = 30 000（按 128k→30k 比例随窗缩放；model_max_output_tokens>0 则覆盖）
usable ≈ 98k tok = 窗 − 输出预留
fill = assembled / usable    ← 分母不是 128k
project_context ≤ 2 000 字；@path prereread ≤ 1 200 字 × 3 文件 × 0.4s
turn_token_budget 默认 0（不限制累计）；超了 Engine 在步前/步后 break，不靠组窗救命
◆ 要点  压缩只作用于本步模型窗。磁盘稿与网页聊天记录通常仍完整。当成 Session 常驻 128k 会规划错内存（4g 上 fat-window 大约 2–4 颗 Turn）。

主链

assemble 本步窗口
    │
    ▼
卫生（几乎每步；settings: tool_result_char_budget=4000 / latest_read=32000）
    1  单条超长 → 头尾截断，中间丢弃并留下可再读指针
       默认 4 000 字；刚刚成功 read_file 的那份可放到 32 000
    2  同路径旧读取折成短占位（只留最近一次全文；更早的留首尾约 300 字与行号）
       被挤出可见窗的路径进入 evicted_paths；每路径每 Turn 允许再读一次
       （evicted_reread_used），不触发 read_after_complete 硬门
    3  成串已完成的旧工具结果折短（不拆当前正在配对的这一次）
    ◆ 要点  卫生不是「超限才压缩」。每步都做，否则 4k 工具结果会在 fill 到 0.80 之前先撑爆 usable。
    │
    ▼
填充率加压（CompactionPolicy）
    ≥0.80  collapse：中间折成占位，留头与热尾（hot_zone_ratio=0.35）
    ≥0.90  snip：从最旧完整消息组删除
    ≥0.95  autocompact：整窗结构化摘要
           compact_timeout=20s · compact_max_output_tokens=1024
           可另配便宜 compact_model_*；失败回退确定性摘要
           默认定增量，不在首 token 前再同步阻塞主模型
    写 context.reported：fill_ratio、strategies、budget_truncated_by_tool、assemble_ms
    ◆ 要点  0.95 若同步调主模型做摘要，R2 破了：用户看见的首 token 前又付一次供应商，且 step 墙钟被摘要吃掉。
    │
    ▼
送给模型
    长文被截断时附标题大纲（Markdown/纯文本抽标题，Python AST），使模型跳段而非从第一行盲翻
    编码场景仍不以 search_sources 导航长代码；Locate 是符号表+LSP，不是这一层
    tools[] 晚期禁用不改 schema 字节（见工具面）
