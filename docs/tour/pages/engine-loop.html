AgentEngine 单循环：一次推理步如何完成

AgentPlatform 的一次 Turn 通常包含多轮模型请求和工具执行。模型根据当前上下文返回文本或提出工具调用，运行时将工具结果并入消息历史，再把更新后的上下文交给模型。AgentEngine 负责这段循环：组织每一步的上下文、消费模型流、执行工具，并根据响应决定继续推理还是进入终局处理。

这条循环运行在 TurnController 管理的 Turn 生命周期之内。Controller 负责领取 Run、编译用户输入、注入场景对应的提示词与工具集合，并在任务完成、失败、取消或等待审批时维护外层状态；Engine 不领取 Run，也不直接写入 Turn 的最终状态。模型请求结束并不意味着 Turn 已完成：工具结果、审批中断和终局前的验证要求都可能使 Engine 继续执行下一步。

1. 从请求进入 Engine

Controller 领取 Run 并写入 turn.accepted 后，先由 InputCompiler 处理输入。除了解析斜杠指令，它还会预读用户通过 @path 指定的文件；单文件预读上限为 1,200 字符，超时 0.4 秒，一次最多处理 3 个文件。随后 should_query 判断当前请求是否需要调用模型。/help、/compact、/verify 等可以走本地处理的路径不会进入 Engine 的循环；/compact 使用独立的摘要请求，超时为 20 秒、输出上限为 1,024 tokens，失败时回退到确定性摘要。此类本地结束记录 termination_reason=local_response，不占用 Engine 步数。

需要模型处理时，Controller 根据 ScenarioProfile 生成工具范围、系统提示和生成参数，再创建 TurnState 与 ModelGateway，随后调用 AgentEngine.run(state)。Engine 不根据场景名称分支；场景差异通过 Controller 注入的工具集合、提示词和步数预算体现。当前默认步数上限如下，未单独配置的场景使用 40 步。

场景max_steps配置侧重点
agent（编码） 150 仓库导航、文件修改、命令执行和测试工具。
writing（写作） 40 草稿、大纲、资料检索、引用检查与写作状态管理。
intel（情报） 40 情报资料检索及 IOC 相关工具。
collab（协作） 50 通过指定的子代理类型与工具集合分配任务。
其他或未设置上限 40 使用通用默认值。

通过 delegate 启动的子 Agent 默认最多执行 12 步，但子代理的工作仍计入父 Turn 的总步数预算。因此，委派可以把任务交给不同能力的执行单元处理，却不能扩张父任务允许的整体执行量。

2. 一步模型循环的执行顺序

Engine 以 state.step_count < state.max_steps 控制常规迭代。每一轮开始前先检查累计 token 预算和取消状态；累计用量参数 turn_token_budget 默认值为 0，表示不设置本 Turn 的总 token 上限；如果单独配置了输入或输出 token 限额，仍会按对应限额终止执行。通过检查后，Engine 才递增 step_count 并写入 step.started。单步计时使用 monotonic 时钟，从这时开始计算，涵盖后续组窗、模型流和工具调度，不仅是模型供应商的响应时间。

2.1 组装当前上下文

Engine 根据本步可用工具生成工具描述，再由 ContextEngine.assemble_async 整理消息历史。组窗过程会执行上下文卫生和压缩策略：普通工具结果默认截断到 4,000 字符；刚刚成功读取的文件内容可保留到 32,000 字符。对于默认 128K token 的上下文窗口，系统约留出 30K tokens 作为输出空间，因此组窗填充率以可用输入预算而不是整个窗口作为分母。

当填充率达到 0.80 时，系统先折叠较早的上下文组，并保留热尾约 35% 的内容；达到 0.90 时，再裁去最旧的上下文组；达到 0.95 时，触发自动压缩。具体采取了哪些策略、填充率以及工具结果截断情况会写入 context.reported，便于定位模型输入为何发生变化。原始消息快照和 envelope 哈希则以后台任务方式记录，不会并入送给模型的上下文。

工具表默认保持稳定。即使进入交付末段或剩余步数较少，运行时也优先在 handler 入口拒绝晚期不应再用的 search_sources、delegate、remember 和 recall，而不是从 tools[] 中删除其 schema。触发条件是交付状态已为 ok 或 warning，或 step_count 至少为 8 且剩余步数不超过 6。保持工具 schema 字节稳定，是为了避免无必要地改变发送给模型的前缀，破坏供应商的 prefix cache。

2.2 请求模型并消费流式响应

ModelGateway 提供统一的模型流接口。默认 Compose 部署中的 live 请求由 RemoteModelProvider 通过 HTTP NDJSON 发送到 model-gateway 的 /internal/v1/complete；stub 和 recorded 模式则在编排进程内运行，不经过独立网关。查询 Embedding 和资料索引走 retrieval 服务，命令执行走 sandbox 平面，这些调用不属于模型网关的同一条请求链。

模型侧存在三层时间约束：连接建立默认 10 秒，首字节等待默认 60 秒，整段响应流最长 600 秒；Engine 的单步墙钟上限是 720 秒。首字节超时、连接失败、429 或 5xx 等可重试错误只有在还没有向用户输出响应内容时才允许重新请求，最多重试 2 次，退避间隔从 0.5 秒逐步增加到 8 秒。响应已经开始输出后，如果流中途断开，运行时不会从头重放已经送出的 token，否则已发送给用户的文本可能被重放。

取消请求会由独立的 asyncio 任务持续检查，轮询间隔约为 50 毫秒。检测到取消后，Engine 会中止模型网关的 HTTP 请求并关闭异步生成器，避免用户取消后上游模型仍继续生成并消耗资源。流中的取消检测不在每个 token 到达时另做一次数据库往返；取消监视器负责触发中断，chunk 循环只读取已经更新的状态。

流式数据进入不同的事件通道。可见文本增量写为 turn.token；在默认 EVENT_DURABILITY=checkpoint 模式下，高频增量通过 Redis live 通道发布，EVENT_DURABILITY=all 时才将其批量写入 PostgreSQL 的耐久事件表。模型的 thinking / liveness 增量使用 turn.thinking.delta，默认不进入 turn_views；Ops 评测可以将其转存到 sidecar。工具调用虽然在响应流中逐步解析，但不会在模型还没结束输出时执行。Engine 收完一段响应后先记录 usage.reported，再根据本步实际 token 用量重新检查预算，避免单次响应跨过预算上限后仍被当成普通终稿。

3. 工具批处理与结果合并

模型给出 tool_use 后，Engine 先将这批调用按模型返回的顺序保存，再交给 _run_tool_batch。连续出现的只读调用可以并行执行，写文件、编辑文件、命令执行和其他有状态变更的操作则串行处理。可并行的读取工具包括 list_dir、glob、grep、read_file、search_sources、enrich_ioc 和 lookup_indicator；声明为只读的 delegate 也可根据 agent_type 进入并行批次。

并行只读调用不能共享同一份可变的 state.messages 和 read_registry。Engine 为每个调用建立隔离副本，并在所有调用返回后按原始 tool_use 顺序合并工具消息和读取登记结果。实际 I/O 的完成顺序不固定，合并后的顺序却必须稳定，因为消息中的工具结果需要与模型发出的调用逐项对应；如果让并发任务直接修改同一份状态，完成顺序就可能改变对话结构或造成竞态。

本 Turn 内还维护了读取缓存和调用预算。对相同参数的可缓存读取，重复调用会复用已取得的结果并附带提示，要求模型不要继续重复请求同一内容；失败结果不进入缓存。read_file 每 Turn 默认最多执行 16 次，search_sources 最多执行 3 次。超出预算时，Engine 把跳过或失败信息作为工具结果返回给模型，并记录相应事件。

工具执行结果仍由 Engine 统一收口。每次调用都有 tool.started 和 tool.completed 事件，结果再作为 tool message 加入后续上下文。search_sources 的向量检索、关键字回退等逻辑通过 retrieval / embedding 服务完成；run_command 和 run_tests 默认发往 sandbox 平面，部署未配置独立平面 URL 时才回退到编排进程内的 Landlock / bubblewrap 隔离路径。评测场景中的 pytest 与环境探针命令会路由到对应题目的 Docker 环境，而不是直接执行宿主 shell。

少数工具会在 handler 层改道，以保持模型可见的工具 schema 稳定。例如，grep 的参数表现为符号定位请求时，执行会转到 search_codebase 的 Locate 路径。模型仍以 grep 发起调用，实际执行路径则通过 redirected_from=grep 记录，调用记录与执行行为可以对应起来。

工具超时与审批中断

单个工具的默认墙钟超时为 60 秒；结构导航默认为 15 秒，结构诊断为 60 秒，编辑后单文件增量检查为 30 秒。工具超时会以 tool.completed(status=timeout) 记录，超时结果同时写回消息历史，让模型可以判断是否调整策略；它本身不会直接把整条 Turn 标记为失败。工具墙钟与 Engine 单步的 720 秒上限独立计算，一步中包含模型响应、多个并行读取和串行工具时，不能用工具的 60 秒默认值来推断整步的最长耗时。

如果 handler 返回 approval_required，Engine 会生成 approval.requested 事件，保存待审批工具调用，并以 waiting_approval 返回给 Controller。Controller 将 TurnState 和中断信息持久化为 checkpoint，Turn 转入审批等待状态，而不写入 turn.completed。此时该 Turn 已从当前进程的 active 执行集合移除；用户批准或拒绝后，系统恢复原 checkpoint，在相同 run_id 和 step_count 上继续执行，不另开一条 Turn。

审批界面所需的差异内容也会随调用类型变化。write_file 会附上最多 32,000 字符的旧文件内容和新内容，供界面展示整体差异；edit_file 只附上修改区间的 old/new 文本。审批期间等待的是用户决策，不是 Engine 正在运行的一个 step，因此它受独立审批超时约束，也不应被当作常规的无进展执行处理。

4. 终局判断与验证续跑

当一批工具执行完毕且没有触发取消、审批挂起、子任务等待或明确终止信号时，Engine 会把工具结果保留在消息历史中，再进入下一次迭代。只有模型没有提出 tool_use、而是返回了终稿文本时，流程才进入终局判断。终局判断仍可能要求继续一轮，因此“模型已经写出正文”并不等于当前 Turn 一定完成。

编码任务的验证收据由工具结果维护的状态触发，而不是从终稿文本推断。第一类情况是最近一次代码编辑成功后尚未执行测试类命令；第二类情况是仓库测试已经通过，但 problem.md、PROBLEM.md 或 issue.md 中提取出的复现义务尚未在最近编辑之后得到满足。收据只在剩余步数足够时注入，默认需要保留 10 步；同一类别每 Turn 最多发送一次，用户取消或 token 预算已经耗尽时不注入。

命中时，平台向消息历史追加一条 user message，明确要求补充验证或完成问题复现，同时写入 tool.completed 事件，标记 tool_name=verify_receipt 与 verify_receipt=true。这不是注册给模型调用的普通工具，也不显示在工具菜单中；Engine 通过 continue 回到同一个 while，重新组装上下文并请求模型。验证因此仍属于当前 Turn 的终局边，而不是额外增加一个图节点或创建新的 Turn。

写作场景另有交付门检查。若当前场景为 writing，Turn 尚未取消或耗尽预算、仍至少保留一步，并且持久化的交付 manifest 还有阻塞项，Engine 会注入交付提示并继续循环；用户明确发起的同 Turn 交付收据抑制条件也会参与判断。这个路径与编码任务的测试收据不同：前者核对写作交付状态，后者依据文件编辑和测试结果维护验证义务。

5. 时间预算与停滞判定

不同时间限制观察的是不同对象。模型超时限制供应商请求，工具超时限制单次 handler，Engine 单步时限涵盖整轮的组窗、推理和工具调度；Run 租约则决定哪个 runtime 副本拥有执行权。停滞看门狗观察的是耐久事件是否继续更新，不能用这些时限中的任意一个取代其余机制。

机制默认值超时或异常后的处理
连接建立 10 秒 归类为请求异常；在允许重试且未开始输出时可重试。
等待模型首字节 60 秒 作为 transient 错误处理；最多重试 2 次，退避 0.5–8 秒。
模型整段流 600 秒 以模型供应商超时结束本次请求。
Engine 单步 720 秒 StepTimeoutError，最终以 step_timeout 失败。
一般工具 60 秒 写入 tool.completed(status=timeout) 并把结果交回模型。
结构导航 / 诊断 / 编辑后检查 15 / 60 / 30 秒 按工具超时返回结果，不等同于 Turn 超时。
/compact 摘要 20 秒，输出最多 1,024 tokens 失败后使用确定性摘要。
Run 租约 TTL 180 秒；心跳 10 秒 维护执行所有权，避免长时间运行时被误回收。
停滞看门狗 每 30 秒扫描；180 秒无新耐久事件 默认自动以 step_timeout 结束停滞 Turn。
审批等待 600 秒 等待超时按审批失败处理；不作为正常 Engine step 执行。
进入 Engine 前的领取等待 15 秒 未能开始执行时记为 start_timeout。

720 秒的单步上限高于 600 秒的模型流上限，是为了让模型层先报告自身请求超时，并给组窗及工具调度留出时间。Run 租约 TTL 设为 180 秒，是因为编码任务的一步在并行读取和模型请求负载下常持续 60–160 秒；过短租约可能在事件写入竞争时回收仍在运行的 Turn。它们解决的是不同层面的生命周期问题，不能合并成一个统一的超时值。

停滞看门狗查询 turn_events 的最新耐久事件时间，而不是判断前端是否仍收到 live token。默认 checkpoint 模式下，高频文本增量可以只经 Redis live 通道发送，因此 Engine 在长模型流期间每约 45 秒写入一次耐久的 turn.thinking 存活事件，保持看门狗可观察到执行仍在推进。Ops eval 将 thinking 内容转存到 sidecar 时，会用 15 秒的数据库心跳维持存活信号。若把流式增量移出耐久事件表，却不再保留心跳，正常运行的长请求就可能被误判为停滞。

看门狗默认跳过 waiting_child；waiting_approval 则使用独立的 600 秒审批期限。取消请求也有单独的收尾路径：正常取消以 cancelled 结束，不应被归类为一般失败；若取消标志已写入但执行器已经丢失，Watchdog 会尝试完成 orphan cancel，而不是再把它当作普通停滞报警。

6. Engine 的职责边界

AgentEngine 管理一次 Turn 内的推理步骤、上下文组装、模型流、工具调度、工具结果登记和终局前的继续条件。Run 领取与租约、斜杠指令编译、审批 checkpoint 的持久化以及最终 turn.completed、turn.failed 或 turn.cancelled 等终态由 TurnController 负责；具体工具行为位于 tools.*，上下文填充率和压缩阈值由 context.policy 管理，停滞扫描运行在旁挂的 Stall Watchdog 中。

这条主链可以概括为：assemble → model stream → parse output → tool batch or final-edge check。工具调用会把控制权带回循环，终局收据也通过同一循环的 continue 续跑；耐久状态则由 step.started、工具事件、用量报告和最终状态事件形成边界。事件投影、live 增量和耐久记录承担不同职责，不应把它们画成互相独立的第二套推理流程。
