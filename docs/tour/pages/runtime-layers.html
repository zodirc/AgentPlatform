Runtime 分层：职责边界与执行平面

Agent 执行一项任务时，通常由模型推理与工具执行交替完成。模型根据用户目标和当前上下文决定下一步动作，运行时调用相应工具，再把结果加入后续推理所使用的上下文。任务可能经历多轮模型请求和工具调用，也可能在执行中等待审批、接收取消请求，或因模型服务、数据库和执行环境故障而中断。运行时必须在这些状态变化之间保持任务记录的一致性，同时限制每一步的执行时间和资源消耗。

AgentPlatform 将这些职责划分为运行时编排层和执行平面。编排层负责 Turn 的生命周期与推理循环；模型网关、检索服务和沙箱分别承接模型请求、Embedding 与资料索引、隔离命令执行。这个边界将任务状态管理留在编排层，把长连接、模型计算和操作系统级隔离放在独立服务中，使下游服务的耗时与故障不会直接改变 Turn 的状态机。本节中的执行平面专指默认 Compose 部署下由独立容器提供的能力；测试或兼容部署可以将其中部分能力保留在同一进程内。

1. 运行时的职责划分

1.1 Controller、Engine 与场景配置

运行时编排层将 Turn 生命周期管理与推理循环分开，由 TurnController 和 AgentEngine 分别承担。场景配置与外部执行服务位于这条主路径的两侧：前者决定本次 Turn 使用哪些能力，后者承接需要独立资源或执行隔离的操作。各组成部分的职责如下。

组成部分主要职责
TurnController 领取 Run，建立本次 Turn 的执行上下文，处理取消和审批续跑，并写入终态。
AgentEngine 在循环中组装上下文、请求模型、解析输出并调度工具；维护 TurnState 并追加过程事件。
ScenarioProfile 声明场景可用工具、系统提示、步数预算、生成参数和审批覆盖，由 Controller 在启动时加载。
独立执行服务 model-gateway 承接 live 模型请求，sources-retrieval 承担 Embedding 与资料索引，sandbox 执行受操作系统隔离的命令。默认 Compose 部署通过内部 HTTP 调用这些服务。

这一边界同时约束状态写入权：Controller 管理 Turn 生命周期并写入终态，Engine 推进执行过程并追加过程事件。Engine 不领取 Run，也不管理执行租约。发生审批挂起时，Controller 保存 Engine 的当前状态，待用户批准或拒绝后恢复同一次执行；如果 Engine 在循环中自行写入完成状态，续跑就可能失去原有 checkpoint、Run 身份和验证追踪。

1.2 一次 Turn 的执行路径

API 接收请求后，将 Turn 与对应的 Run 写入 PostgreSQL，再通过分发通知唤醒运行时。默认配置使用 Redis Pub/Sub 发送 turn.dispatch 通知；该通知只用于唤醒执行器，不代表执行权已经转移。真正的领取由 PostgreSQL 中的条件更新决定，只有状态为 accepted 的 Run 可以被领取。领取成功后，运行时记录持有该 Run 的租约，并通过心跳维持执行权。

Controller 随后加载对应的 ScenarioProfile，由 InputCompiler 处理斜杠指令、@path 预读和会话历史。/help、/compact、/verify 等可以在本地处理的请求，不必进入模型推理循环；需要模型处理时，Controller 才会进一步组装工具范围、模型网关和 TurnState，并把执行交给 Engine。

Engine 每一步先检查取消状态和预算，再组装当前上下文并请求模型。模型可以直接返回面向用户的文本，也可以提出工具调用；运行时解析返回内容后执行相应工具，并将结果加入后续上下文。循环受到 Profile 中 max_steps 的限制，同时受 Engine 单步超时和 Turn 级预算约束。若任务仍有未完成的验证义务，Engine 可以通过 verify_receipt 的续跑逻辑继续处理，而不是把验证工作另建成一个新 Turn。

普通工具由 runtime 中注册的 handler 执行；需要独立资源或操作系统级隔离的操作才会转交相应服务。live 模型请求通过 model-gateway 以 HTTP NDJSON 流式返回，Embedding 和资料索引工作由 sources-retrieval 承担，命令执行则在默认 Compose 部署中进入 sandbox，由 bwrap 和 Landlock 提供操作系统级隔离。

Engine 通过事件写入器记录步骤、工具调用、用量和上下文报告，Controller 在任务完成、失败或取消时写入终态。PostgreSQL 保存 Turn 的权威状态和耐久事件；默认 checkpoint 持久化模式下，高频 token 与 thinking 增量可通过 Redis live 通道发送，不必把每个增量都写入耐久事件表。API 将耐久状态与 live 事件投影到工作台的 SSE 流，供界面展示执行进度并在断线后恢复状态。

2. 场景差异通过 Profile 配置

写作、编码、情报和多助手协作在工具能力、提示词和生成参数上有不同需求，但这些差异不要求各自维护一套推理循环。ScenarioRegistry 从 profiles/*.yaml 加载不可变的 ScenarioProfile，Controller 在启动 Turn 时选择相应配置，再组装工具表、提示词和生成参数。新增场景能力时，应先判断差异能否通过 Profile 表达；只有执行机制本身确实不同，才有必要修改 Engine 主循环。

场景max_stepsProfile 配置侧重点
agent（编码） 150 仓库导航、文件修改、命令与测试工具，以及结构化导航预热。
writing（写作） 40 章节草稿、大纲、资料检索、引用检查和写作状态管理。
intel（情报） 40 情报资料检索与 IOC 相关工具。
collab（协作） 50 通过指定的子代理类型和工具集合分配任务。
未指定场景上限 40 使用默认步数预算。

max_steps 是执行预算，不意味着不同场景拥有不同的主循环。Engine 仍以 state.step_count < state.max_steps 控制常规循环；如果验证状态要求继续执行，则由 verify_receipt 的续跑逻辑推进。通过 delegate 启动的子 Agent 默认拥有独立的 12 步上限，但其执行仍计入父 Turn 的步数预算，因而不能通过委派绕开父任务的整体限制。

生成参数也由 Profile 提供。例如，writing 的默认 temperature 为 0.8；agent 可以不显式设置 temperature，沿用模型提供方的默认行为。结构化导航能力同样通过 tool_names 声明，而不是独立的 feature flag。任务开始后，不应再把这些工具从工具表中临时裁掉，否则同一 Turn 的能力边界就会随执行过程发生变化。

3. 租约、超时与停滞检测

运行时需要处理几种性质不同的故障：执行器可能失去对 Run 的所有权，模型请求可能迟迟没有响应，单步执行可能超过预算，任务也可能在没有新事件的情况下挂起。租约、请求超时、Engine 单步超时和停滞看门狗分别观察不同对象，不能用其中一项代替其他项。

机制当前默认值作用范围
Run 租约 TTL 180 秒；心跳 10 秒；事件路径上的机会续租最小间隔 5 秒 记录哪个 runtime 副本持有 Run 的执行权。
模型请求 连接 10 秒；首字节 60 秒；整段流 600 秒；最多重试 2 次 限制建立连接、等待模型开始响应及消费完整流的时间。
Engine 单步 720 秒 限制一次推理循环中组窗、模型请求与工具调度的总执行时间。
一般工具 默认 60 秒 限制单个工具调用的执行时间。结构导航默认 15 秒，结构诊断 60 秒，编辑后的增量检查 30 秒。
停滞看门狗 每 30 秒扫描；180 秒没有新耐久事件时判定停滞；默认自动失败 检查耐久事件是否持续更新，并收尾无进展的执行。
审批等待 600 秒 限制 Turn 处于 waiting_approval 的最长等待时间。

Run 租约用于避免多个 runtime 副本重复执行同一任务。只有 accepted 状态的 Run 可以被领取；已经进入 running 的 Run 不会被另一个副本重新领取，否则可能导致相同工具调用执行两次，并生成重复的事件流。编码任务在并行读取和模型请求负载下常持续 60 至 160 秒，因此租约不能沿用早期的 60 秒 TTL：事件写入发生竞争时，过短的租约会把仍在执行的 Turn 错误回收。当前租约参数见上表。

模型请求和 Engine 单步具有各自的时间上限。模型请求分别限制建立连接、等待首字节和消费完整响应流的时间；重试只适用于尚未向用户输出内容、且失败类型允许安全重试的情况。已经输出部分内容后，运行时不会从头回放整条响应。Engine 单步的上限略高于完整模型流的上限，以免合法的长请求先被单步超时截断。单个工具另有独立时限，避免某次工具执行无限占用当前 step 的预算。

停滞看门狗检查 turn_events 是否仍在产生新的耐久记录，而不是判断模型流是否仍有 token 到达。处于 waiting_approval 的 Turn 会被跳过，因为等待用户操作本身可能持续数分钟；已经请求取消但处于 orphan 清理路径中的任务也不会按普通停滞处理。没有新耐久事件并不必然表示推理停止，判断是否停滞还要考虑流式数据采用哪种持久化方式。

默认 checkpoint 模式下，高频流式增量可以只经 Redis live 通道发送，因此运行时还会每 45 秒写入耐久的流存活事件，供看门狗判断长时间模型流是否仍在推进。Ops eval 将 thinking 内容转移到 sidecar 时，另有 15 秒的数据库心跳机制。若只把流式内容移出事件表，却没有保留耐久存活记录，正常运行的长请求也可能被看门狗当作停滞任务终止。

取消请求先写入 PostgreSQL，使其他 runtime 副本也能读取取消意图。Engine 会在步骤边界检查取消状态；模型流进行期间，独立的取消监视任务还会中断正在进行的流和相应 HTTP 请求。用户主动取消的 Turn 以 cancelled 收尾，不应归类为一般执行失败；强制取消走 cancel_force 路径。Run 领取等待超过 15 秒而尚未进入 Engine 时，则按 start_timeout 处理。

进程级 Turn 上限并不等同于系统实际可同时处理的模型请求数。RUNTIME_MAX_INFLIGHT_TURNS=16 是单个 runtime 进程正在执行的 Turn 软上限；转交为审批挂起的 Turn 会从该进程的 active 集合移除，因此该值既不代表所有非终态 Turn 的总数，也不能保证 16 个模型请求同时运行。模型调度器默认提供全局 4 个并发槽位、每租户 2 个槽位，运行时数据库连接池默认最大 5 个连接；高负载下，这两类资源都可能先于 Turn 上限饱和。

4. 审批挂起与同一次执行的恢复

工具调用需要用户批准时，Engine 不会把它当作普通工具失败，也不会将 Turn 标记为完成。Engine 记录待审批的工具调用，写入 approval.requested 事件，并返回控制结果 waiting_approval。该值是运行时用于暂停推理循环的控制信号，不是面向用户的普通文本；如果子代理需要把完全相同的字符串作为摘要返回，必须使用可识别的编码前缀，以免父循环将摘要误判为审批挂起。

Controller 接管挂起状态后，将当前 TurnState 序列化到 checkpoint，其中包括消息、步数上限、验证追踪和其他续跑所需状态，并保存待执行调用的 Profile、工具表与模型配置。Turn 状态变为 waiting_approval，Run 进入 interrupted；此时不会写入 turn.completed，因为任务尚未完成。等待审批的 Turn 不再占用该进程的 active 执行集合，用户的等待时间也不会消耗 Engine 的执行循环。

用户批准或拒绝后，runtime 从内存中的 PendingTurn 或持久化 checkpoint 恢复状态，在同一个 run_id、同一个 step_count 上继续执行。批准时，运行时执行原先挂起的工具调用；拒绝时，则把拒绝结果写回工具消息，再由 Engine 继续推理。恢复原状态可以保留此前累积的上下文和验证义务，避免审批续跑被误建成新 Turn 后重置 verify_* 追踪或重复执行已经完成的步骤。

write_file 的审批记录会包含截断后的全文件旧文，edit_file 则只保留相关修改区间。批准或拒绝命令还必须由持有对应 Run 的 runner 处理，并防止并发命令同时恢复同一个 checkpoint，否则重复点击或 HTTP 重试可能造成同一工具调用被执行两次。
