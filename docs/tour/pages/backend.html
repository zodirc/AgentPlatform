后端架构：进程、状态与负载

AgentPlatform 的一次请求会经过工作台、API 和运行时编排，再由模型网关、检索服务或沙箱完成具体操作。请求进入系统时，API 负责身份校验、准入和任务记录；运行时取得任务执行权后，才开始推理循环；执行期间产生的状态变化写入 PostgreSQL，并由 API 整理成工作台可以消费的事件流。独立执行服务通过内部 HTTP 与运行时通信，不直接向浏览器提供事件流，也不负责决定一个 Turn 是否已被领取或完成。

这套架构需要把三类职责分开。任务状态与执行权以 PostgreSQL 为准，Redis 负责唤醒和实时分发，模型、检索与命令执行由各自的执行服务承接。 三者不能相互替代：分发通知丢失不能导致任务遗失，实时 token 丢失不能改变已经提交的任务状态，执行服务返回结果也不能绕过运行时写入 Turn 事件的流程。

本文从部署进程、数据归属和资源边界解释后端架构。一次请求经过哪些步骤见请求主路径；模型调用、上下文组装和工具调度的循环内部细节见Engine 单循环。

1. 部署分层与职责边界

默认 Compose 部署将后端拆成多个进程。拆分的目的不是把每个函数都变成服务，而是把生命周期管理、外部请求、重计算和操作系统隔离分别放在适合的执行环境中。

进程或服务职责与边界
Caddy 对外提供 HTTP/HTTPS 入口，将 /api/* 与健康检查路径转发给 API，其余路径交给 Web。它不校验用户会话、不保存 Turn 状态，也不解析 SSE 事件。
web 提供工作台页面，通过 API 获取视图，并订阅 Turn 的 SSE 事件。浏览器不直接连接编排进程或执行平面。
api 负责用户身份与会话归属检查、请求准入、创建 Turn/Run、提供视图查询、接收审批和取消命令，并将后端事件整理为 SSE。它不承担 Agent 推理循环。
postgres 保存 Turn、Run、耐久事件与界面投影等业务状态；Run 的领取通过数据库条件更新完成。检索也会使用 PostgreSQL/pgvector，但检索请求由检索服务负责。
runtime 执行编排逻辑：领取 Run、持有租约、建立 TurnState、运行 Engine、处理审批续跑，并写入过程事件和终态。运行时不直接向浏览器提供 SSE。
model-gateway 转发 live 模型请求，并以 HTTP NDJSON 流返回上游响应。模型流的网络连接由网关承接，runtime 保留推理循环和任务状态。
sources-retrieval 负责资料同步、索引维护、Embedding，以及 ANN/FTS 检索。默认执行平面部署将 Embedding 模型权重集中在此服务，运行时通过 HTTP 请求查询向量。
sandbox 执行需要操作系统级隔离的命令。默认部署通过独立服务调用 bwrap / Landlock 等隔离机制；测试或兼容模式可以回退到运行时进程内的实现。
redis 提供 turn.dispatch、turn.live.* 等 Pub/Sub 通道，并通过 Streams 承载可延迟处理的索引任务。Redis 不决定 Run 的所有权，也不是耐久事件的权威存储。
旁路进程 ast-indexer、评测服务及发布台承担结构索引、评测和运维任务，不属于每次普通提问都必须经过的主链。

这些职责划分同时限定了状态写入权。API 创建任务并提供面向浏览器的访问入口，运行时负责推进任务状态和写入执行过程，执行平面只返回模型、Embedding 或命令执行结果。检索服务可以写入资料索引，但不写 Turn 的耐久事件；模型网关与沙箱不应直接更新任务状态。这样，某个平面的失败可以作为运行时处理的调用失败，而不需要让每个服务分别维护一套 Turn 状态机。

2. 业务状态、耐久事件与分发通道

理解后端最重要的区别，是把业务记录、耐久事件和通知通道分开。它们经常在同一个执行阶段出现，但承担的职责并不相同。

数据或通道写入方与读取方用途和保证
turns、runs API 创建初始记录；运行时领取 Run，并更新执行中或终态状态 保存任务生命周期与执行权相关状态，是调度和状态查询的依据。
turn_views API 创建初始投影，并根据耐久事件更新 为列表、首屏和审批界面提供读取视图。它是投影，不替代 turn_events 中的耐久记录。
turn_events 运行时写入；API 读取并向 SSE 回放 保存步骤、工具调用、审批和终态等耐久事件。事件 sequence 用于排序与断线后的追赶。
run_commands API 写入审批、取消等控制命令；持有对应 Run 的运行时消费 把用户控制动作交给当前执行者处理，避免浏览器直接操作运行时内存状态。
turn.dispatch（Redis Pub/Sub） API 在事务提交后发布；运行时订阅 作为待领取任务的唤醒信号。通知可能丢失，因此运行时仍会轮询数据库；实际领取权由 PostgreSQL 中的条件更新决定。
turn.live.*（Redis Pub/Sub） 运行时发布 token、thinking 和工具增量；API 订阅并转发 承载高频实时内容，不提供 PostgreSQL 的耐久 sequence，也不作为断线恢复的完整日志。
PostgreSQL NOTIFY 事件写入或命令提交后通知监听进程 用于唤醒投影、事件回放或命令消费。通知本身不包含完整耐久事件，也不承担任务所有权仲裁。
agent.jobs（Redis Streams） API 或旁路任务生产者写入；检索服务消费 承载资料索引等可延后完成的任务，不用于领取 Turn。

默认配置使用 PostgreSQL 保存业务状态和耐久事件，Redis Pub/Sub 用于分发唤醒和实时内容。两种路径不能混为一谈。turn.dispatch 在任务记录提交后发布；若通知丢失，运行时可以通过周期性轮询发现仍处于 accepted 且符合领取条件的 Run。多个运行时副本竞争同一 Run 时，数据库条件更新（CAS）决定哪个副本获得执行权；不能把 Redis 消费成功当作 claim 成功。

turn_events 与 turn.live.* 采用不同的恢复语义。耐久事件带有 PostgreSQL 分配的 sequence，客户端重连时可以依据 Last-Event-ID 或 since_sequence 重新读取缺失的耐久事件。默认 EVENT_DURABILITY=checkpoint 模式下，高频 token、thinking 和工具增量优先通过 turn.live.* 传输，不必逐条写入 turn_events；耐久状态和工具边界事件仍然落库。因而重连可以恢复权威状态与耐久事件，但不保证逐 token 重播此前所有实时增量。若启用 EVENT_DURABILITY=all，增量事件会进入耐久事件表，并通过约 40 毫秒的批写窗口合并写入；Redis 实时发布失败时，写入器会回退到 PostgreSQL。

3. 一次 Turn 如何经过后端

请求主路径可以分成提交、领取、执行、事件返回和控制命令五个阶段。它们使用不同的连接和资源，不能仅凭 HTTP 响应时间推断任务已经开始推理。

请求提交与准入

工作台通过 POST /api/v1/sessions/{sid}/turns 提交用户消息。API 先验证用户会话身份，并检查当前用户是否拥有目标 Session，再确定场景和相关请求参数。默认的 pull 调度模式会在创建任务前检查尚未领取的队列深度：全局默认上限为 32，同一用户默认上限为 2。达到上限时，API 返回 429 Too Many Requests 和 Retry-After: 5，此时新 Turn 尚未插入数据库；如果携带的 client_request_id 命中已创建请求，则按幂等重放处理，不再重复创建任务。

准入检查通过后，API 在同一数据库事务中创建 turns、runs 和初始 turn_views 记录。事务提交后再发布 turn.dispatch 唤醒信号，并向客户端返回 HTTP 202 Accepted。这个响应表示请求已经进入调度流程，不代表运行时已开始执行。运行时领取成功后，才会写入第一条耐久的 turn.accepted 事件，因此把 202 当作推理开始时间会将排队耗时错误地算进模型执行时延。

运行时领取与任务执行

默认 pull 模式下，运行时订阅 turn.dispatch，同时每隔约 2 秒轮询数据库以弥补 Pub/Sub 通知丢失。候选 Run 只有在数据库条件更新成功后才会被该副本领取；领取后运行时记录执行租约，并按默认 10 秒间隔发送心跳。租约 TTL 默认 180 秒，主要用于识别失去响应的执行者，而不是限制单次模型调用本身的时长。

Controller 在进入 Engine 前处理输入编译和本地指令。斜杠指令、@path 预读与会话历史在这一阶段组装；可以本地完成的 /help、/compact 或 /verify 请求可能不需要进入模型循环。需要推理的请求才会加载对应场景的工具表和提示词，并交由 AgentEngine 组装上下文、请求模型、调度工具。该循环内部由Engine 单循环单独说明，本页只强调它与后端各执行服务的连接关系。

默认 Compose 部署中，live 模型请求通过 HTTP NDJSON 发送到 model-gateway；search_sources 所需的 query Embedding 通过 HTTP 请求 sources-retrieval；run_command 和 run_tests 等命令执行请求进入 sandbox。三条调用路径不共享 Redis Streams 作为热路径。Redis Streams 面向资料索引等可延迟任务，而同步查询或执行的结果必须直接返回当前 Turn。

事件返回与浏览器订阅

工作台通常在收到 202 后立即对 /api/v1/turns/{tid}/stream 建立 SSE 连接。该 GET 请求会再次进行会话身份验证和 Turn 归属检查；SSE 是独立 HTTP 请求，不能沿用此前 POST 的授权结果。API 的流生成器同时等待 Redis live fan-out、PostgreSQL 通知与短间隔轮询：实时增量可以直接转发，耐久事件则根据当前 sequence 游标从 turn_events 读取。耐久事件带 SSE id，live 事件不带可用于耐久续传的 ID。

SSE 连接只是观看任务进展的通道，不拥有任务执行权。关闭浏览器或断开 SSE 不会自动取消 Turn；大量浏览器挂看主要消耗 API 的文件描述符、协程和连接资源，不等同于同样数量的活动推理任务。当任务结束，或者进入需要用户审批的暂停点时，API 会在投影更新后结束当前流，工作台再读取 /view 以展示权威状态。流空闲期间 API 会发送注释型 ping；客户端若长时间没有收到任何字节，会带着耐久游标重新连接。由于 live 增量没有耐久 sequence，重连不承诺从中断处继续逐 token 回放。

审批与取消命令

审批和取消通过独立的短 POST 请求提交。API 校验调用者是否可以访问该 Turn，将控制命令写入 run_commands 并发出唤醒通知；只有与 Run 的 runner_id 匹配且仍持有租约的运行时副本才处理相应命令。审批批准后，运行时从当前内存状态或持久化 checkpoint 恢复同一次执行，使用原有 run_id 和步数状态处理待审批工具调用；它不会创建一条新 Run 来续跑。当前实现会在 Turn 交接到 waiting_approval 时将其从进程内 active 集合移除，审批决议后重新接管执行，因此“正在等待审批的任务总量”与“本进程当前正在执行的 Turn 数量”是两个不同指标。

4. 入口代理与身份校验

Caddy 仅负责第七层路由与代理转发：/api/* 和健康检查路径发往 API，其他路径由 Web 提供。它不验证 Cookie 或 HMAC，不决定队列准入，也不维护事件序号。当前配置将 Web 和 API 暴露在同一主机下，SameSite=Lax Cookie 因而可用于同源请求；启用 HTTPS 时，Caddy 使用内部 TLS 配置。代理必须保留流式响应的传输行为，否则 SSE 可能被中间层缓冲，导致已经生成的 token 延迟成批到达。

会话身份由 API 验证。浏览器携带的 agent_end_user 会话 token 使用 HMAC-SHA256 校验签名，负载含用户标识、过期时间和密码版本；密码版本不匹配时，旧 token 会失效。API 对修改请求与 SSE GET 分别执行身份验证，并将 Session/Turn 映射回所有者检查，不能仅因为请求中带有已知 turn_id 就允许订阅。X-Internal-Token 属于服务间调用与管理代理的内部凭据，不能作为浏览器会话凭据使用。

5. PostgreSQL 连接与事件写入

运行时将交互热路径和长时间后台数据库操作分到两类连接池。两类池连接的是同一 PostgreSQL 实例，区别在于资源配额与超时预算，而不是数据库或数据副本不同。

连接类型默认大小客户端命令与服务端语句超时典型用途
HOT 热池 最小 1，最大 5 5 秒 Run claim 与租约、耐久事件写入、SSE 回放、视图投影、准入检查、控制命令和 checkpoint/transcript。
BYPASS 慢操作池 最小 1，最大 5 120 秒 AST 与后台索引写入、硬删除 Session、事件保留与清理等允许长时间运行的数据库操作。
独立监听连接 不计入 HOT 池的 5 个槽位 由各监听任务控制 LISTEN/NOTIFY 监听、健康探测等长连接。它们若占用热池连接，会永久减少 claim、事件写入和回放可用的槽位。
检索专用连接 由检索实现管理 按检索实现配置 sources-retrieval 通过专用连接执行 ANN/FTS 查询和索引工作，不占用运行时 HOT 池。

HOT 池为交互事务设置较短的超时，是为了避免慢 SQL 长期占据有限连接，使新任务领取、事件批写和 SSE 回放都排队。BYPASS 池允许更长的执行时间，但不应接管本该快速完成的状态事务。对同一个 Turn 写入 turn_events 时，写入事务通过按 Turn 标识计算的事务级 advisory lock 分配事件序号；它只串行化同一个 Turn 的事件序列，不锁住整张事件表，不同 Turn 仍可并行写入。

6. 并发上限与资源规划

系统中的并发数分别约束排队请求、进程内活动 Turn、模型请求和数据库连接。它们的计数对象不同，不能将这些数字当作一个统一的“系统并发量”。

约束默认值作用范围
未领取队列准入 全局 32；每用户 2 pull 模式下、插入新 Turn 之前检查；超限返回 HTTP 429。
RUNTIME_MAX_INFLIGHT_TURNS 每个 runtime 进程 16 约束该进程正在执行的 Turn 数量；不是集群级总量，也不保证全部处于模型推理阶段。
模型调度槽位 全局 4；每租户 2 限制同时进入模型请求调度器的调用数。
HOT 数据库连接池 API/runtime 每进程默认各 5 约束状态读写、事件批写和回放可使用的并发连接。

实际吞吐取决于这些限制中最先饱和的资源，以及模型提供方限流、上下文大小和单次工具的耗时。一个编码 Turn 即使只计作一个活动任务，也可能长时间占用模型调度槽位，并在事件落库时等待数据库连接；SSE 观看者则占用 API 协程和文件描述符，却不占用 runtime 的 inflight 槽位。因此，软件上限 16 不能直接解释为“可同时进行 16 个满上下文编码任务”。现有容量文档对满窗 Turn 的内存估算约为每个 5–30 MiB，但仓库没有逐 Turn RSS 探针，这一数字只能用于规划，不能作为经过压测验证的容量承诺。

上下文窗口同样影响可承载并发。默认配置的模型窗口为 128,000 token，并预留约 30,000 token 给输出，可用于输入内容的预算约为 98,000 token。组窗填充率达到 0.80 时触发 collapse，达到 0.90 时裁剪较旧内容，达到 0.95 时进入自动压缩路径；普通工具结果默认限制为 4,000 字，最近一次成功的 read_file 结果可以使用 32,000 字的上限。这些约束控制单个 Turn 的组窗大小，但组窗在执行中会产生多份对象与序列化副本，因此 token 数不能简单换算成固定的进程内存量。

默认 planes.yml 为 model-gateway 设置 512 MiB 内存上限、为 sandbox 设置 1 GiB 上限；sources-retrieval 的基础默认值为 4 GiB，可由部署环境覆盖。启用大型 Embedding 模型时，权重内存主要出现在检索服务，而不是编排进程。扩容运行时不会自动复制检索模型权重；应根据 dispatch_queue_depth、dispatch_wait_seconds、event_pipeline_lag_seconds、首字节时延及实际内存观测判断瓶颈，再决定扩展哪个服务。

多副本部署可以增加 runtime 实例，Run 的 claim 仍由共享 PostgreSQL 中的条件更新协调；执行租约和 active 计数则是每个进程自身的状态。默认部署按每个容器运行单个应用进程设计，不应直接通过 uvicorn --workers 在一个 runtime 容器中复制工作进程，因为进程内的 active 集合和监听器会分别复制，单进程计数也就不再代表整个容器的总量。检索负载应单独扩展 sources-retrieval；异步资料索引则通过 agent.jobs 与交互式查询分开调度。

7. 事务与部署边界

创建 Turn 的多条初始记录在同一事务中写入，只有事务提交后才发送默认分发通知。事件序号在每个 Turn 的事务锁下分配，避免两个执行路径为同一 Turn 生成重复或乱序的耐久序号。SQL 使用参数化语句；存储层、服务间 HTTP 和浏览器入口的 TLS/凭据处理仍分别由各自边界负责，不能将内部网络默认可达理解为无需鉴权。

需要核对实现时，可从以下位置继续阅读：API 的 Turn 创建路由、准入队列计算、Controller 与 active Turn 管理、运行时配置、PostgreSQL 连接池、执行平面 Compose 配置和Caddy 路由配置。
