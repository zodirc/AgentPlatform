请求主路径：从提交到 SSE 返回

工作台提交一条消息后，后端需要完成的不只是一次模型请求。API 先验证调用者的身份与 Session 归属，再把 Turn 和 Run 写入数据库；运行时取得 Run 的执行权后，才进入输入编译和模型推理；在执行过程中，耐久事件与高频实时增量通过不同通道返回工作台。将这些阶段区分开，可以避免把 HTTP 接受请求、运行时开始执行和浏览器收到首个 token 当成同一个时间点。

本页聚焦单次请求的端到端路径。后端各进程的职责、数据归属和容量限制见后端架构，组窗、模型流、工具批处理和终局续跑见Engine 单循环。

1. 提交请求与创建任务

工作台向 POST /api/v1/sessions/{sid}/turns 发送消息，并携带会话 Cookie 与 JSON 请求体。Caddy 将 /api/* 转发给 API，但不代替 API 进行认证。API 验证用户身份、检查该 Session 的所有者，并确定本次请求使用的场景及执行参数。

默认 pull 调度模式会在创建任务前执行准入检查。检查依据是仍处于 accepted、尚未被 runtime 领取且对应 Turn 仍为 pending 的 Run 数量；全局默认上限为 32，同一用户默认上限为 2。达到上限时，API 返回 429 Too Many Requests 和 Retry-After: 5，不会先写入一个稍后需要清理的失败 Turn。若请求带有已存在的 client_request_id，API 先查找原请求并按幂等重放处理。

准入通过后，API 在同一 PostgreSQL 事务中创建 Turn、Run 及初始 turn_views 投影。提交事务之后，API 发布 turn.dispatch 唤醒信号，并返回 202 Accepted，响应中包含 turn_id、run_id 与 pending 状态。202 说明请求已进入调度流程，不能用于判断 runtime 是否已经开工；任务的第一条耐久业务事件 turn.accepted 要等到 runtime 真正领取 Run 后才会写入。

2. Runtime 领取执行权

默认 pull 模式下，runtime 订阅 Redis Pub/Sub 的 turn.dispatch，并以约 2 秒为周期轮询数据库，避免通知丢失时任务一直留在队列中。唤醒只触发一次候选查询，是否获得执行权由 PostgreSQL 中针对 accepted Run 的条件更新决定。即使多个 runtime 实例同时看到同一个通知，也只有一个实例能成功完成 claim；Redis 不是任务锁，不能用消费通知的结果判断谁拥有执行权。

领取成功后，runtime 更新 Run 状态、记录持有者与执行租约，并写入 turn.accepted。默认租约 TTL 为 180 秒，心跳间隔为 10 秒。租约记录执行者是否仍有权推进该 Run，与模型请求超时、Engine 单步超时属于不同约束；它的作用是识别失联执行者，避免在正常长请求期间被过早回收。

3. Intake 与 Engine

Controller 在调用 Engine 前执行确定性的输入处理。InputCompiler 处理斜杠指令、@path 预读及会话历史；/help、/compact、/verify 等请求可能在本地完成并直接结束 Turn，不需要进入模型循环。需要模型推理时，Controller 根据请求选择 ScenarioProfile，组装系统提示、可用工具和 TurnState，再调用 AgentEngine。

Engine 每一步组装模型上下文，发起模型请求，并根据模型响应执行工具调用或判断是否可以结束。默认 Compose 部署将 live 模型流通过 HTTP NDJSON 交给 model-gateway，将 query Embedding 交给 sources-retrieval，将命令执行交给 sandbox。这些调用是同步执行路径，需要等当前调用结果回到 runtime 后再进入相应的后续逻辑；资料索引等可延迟工作则通过单独的异步任务通道运行，不应阻塞普通 Turn 的实时查询。

4. 耐久事件和实时增量

运行时把步骤开始、工具执行边界、审批和终态等状态变化写入 PostgreSQL 的 turn_events。每个 Turn 的事件具有耐久 sequence，使事件回放能够按照既定顺序进行。默认 EVENT_DURABILITY=checkpoint 模式下，高频 token、thinking 与工具增量优先发布到 Redis turn.live.*，不逐条写入耐久事件表；启用 EVENT_DURABILITY=all 时，这些增量也会进入 turn_events，并使用批写窗口减少单条事件造成的数据库往返。

这种区分决定了断线恢复的能力。耐久事件有可回放的 sequence，live 增量没有 PostgreSQL 耐久游标，因此客户端重连时能够追赶状态事件，但不保证补回所有已经错过的 token。若 Redis live 发布失败，运行时事件写入器会回退到 PostgreSQL，避免将已经生成的增量只留在一个可能丢失的实时通道中。

5. API 如何向工作台提供 SSE

工作台通常在拿到 202 后立即调用 GET /api/v1/turns/{tid}/stream。该请求会再次校验会话身份和 Turn 归属，因为 SSE 是另一条独立 HTTP 请求。API 通过 Redis 订阅获取 live 增量，并利用 PostgreSQL 通知及短间隔轮询读取 turn_events 中游标之后的耐久事件；耐久事件携带 SSE id，live 事件不提供耐久续传 ID。API 还会根据耐久事件更新 turn_views，而投影不包含全部高频 token/thinking 增量。

SSE 只是事件传输通道，不控制 Turn 的生命周期。关闭页面或中断流连接不会取消后台执行；浏览器重新连接时带上 Last-Event-ID 或 since_sequence，API 根据耐久游标恢复事件。空闲期间 API 发送注释型 ping，客户端若长时间没有任何字节到达，会重新建立连接。审批请求属于一个暂停点：API 等投影状态更新后结束当前 SSE，由工作台重新读取 /view 显示审批界面，用户的批准操作另走短 POST。

6. 审批、取消与异步旁路

审批与取消请求使用独立短 POST 提交。API 将命令写入 run_commands 并发出通知，持有目标 Run 租约的 runtime 副本负责执行。审批批准后，运行时恢复原来的 checkpoint，执行待审批工具，并在同一 run_id 和步数状态下继续 Engine；拒绝则把拒绝结果写入工具结果，再让 Engine 继续决定后续动作。等待审批期间 Turn 处于 waiting_approval，但当前实现会将其从本进程的 active 执行集合移除，因此等待人数不直接占用 runtime 的 inflight 上限。

资料索引不走普通 Turn 的分发流程。API 或其他生产者可以把 sources.index_sync 等任务提交到 Redis Streams 的 agent.jobs，由 sources-retrieval 异步消费；也存在直接调用检索服务同步接口的路径。这些工作不会因为某条用户消息获得了 202 就自动与该 Turn 绑定，也不会把索引任务误记成 run_commands。

实现定位：Turn 创建路由、准入检查、Controller 的领取与续跑、事件写入器、执行平面配置。
