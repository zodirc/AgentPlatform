# 写作模块：修正执行方案

目标是提高小说的吸引力、连续性和语言可信度，同时减少系统自己制造的 AI 味。

本方案不再预设“控制层越完整，小说越好”。目标结构直接采用：

> 最小 Writer 主链，按需 Planner，盲审 Editor，授权 Revision；事实和原文维持连续性，审美信号不进入自动控制。

---

## 1. 结论

前一版方案仍然有旧系统的影子：

- commitment 槽位换成了写作包槽位；
- `story_state` 换成了 canon facts；
- exemplar reward 换成了正向声口样本；
- 自动岛修换成了 Revision Writer；
- `literary / web_serial` 换成了 Planned / Discovery / Hybrid；
- signals 换成了独立 Editor。

这些新设计并非都错，但如果每章强制经过，它们仍会组成一套新的写作官僚系统。

修正后的原则是：

1. 默认路径尽可能短；
2. Planner、事实账、Editor 和修订都有明确入口，不成为每章必经步骤；
3. 规划、写作、编辑和修订使用隔离上下文；
4. 不把难以证明的审美判断放进自动控制回路；
5. legacy 在迁移完成后删除，不长期维护双轨。

---

## 2. 当前实现的实际状态

`writing_architecture=corrected` 已经默认启用，`legacy` 默认关闭。这解决了旧评分、承诺槽和自动文风岛直接控制 Writer 的问题，但尚未达到最终目标。

### 2.1 Planner / Writer 只完成了路径隔离

`writing_pack.py` 仍直接追加：

- outline spine；
- 世界入口；
- 当前阶段；
- 当前章段原文。

这不是完全的“事实化写作包”。如果大纲写着“人物成长、责任、秩序、阶段变化”，这些抽象词仍会进入 Writer，并可能变成旁白总结。

### 2.2 canon facts 还不能可靠维持长篇

当前实现存在：

- 正则只覆盖少量固定句型；
- 每章最后一句自动记为 change；
- 同一 subject 文本变化容易被当成 conflict；
- 人物说法、猜测和叙述事实没有充分区分；
- Writer 读取文件前八条，而不是当前最相关的八条。

它目前更像一个实验性旁路，不能作为强约束。

### 2.3 voice 删除了旧模板，但没有建立作品声口

默认 voice 已经很短，公版样本也不再轮换。但：

- 自动 subtype 仍可能注入“账要当场、信息差写在对话里、狠戾短促”等类型写法；
- 没有本书正例时，Writer 会回到基础模型的默认中文小说分布；
- 删除坏规则不会自动产生好语言。

### 2.4 Editor 调用隔离，但还不是盲审

Editor 仍可能提前看到 L0、`net_signal` 和 detector 结果。这样它容易重复系统判断，而不是独立发现问题。

### 2.5 关闭自动文风岛是必要的，但替代能力尚未建立

现在的默认行为是：

- 文风信号只记遥测；
- 不把 `repair_span` 交给 Writer；
- 不自动修改碎拍、机构开头或设定段；
- 重复大段仍可机械去除。

这能避免错误修稿，却不能改善已经生成的 AI 腔。需要一条用户授权的修订路径，但不能重新变成自动岛修。

## 3. 最小默认路径

默认写作不强制经过完整 Planner、Editor 和 Revision 流水线。

```text
用户要求
→ 当前章必要事实与相关原文
→ 本书已确认声口
→ Writer
→ 落盘
```

Writer 只看：

- 用户消息；
- 当前章具体事实；
- 必要的上一章和相关旧章原文；
- 已确认的世界规则；
- 用户认可的本书片段；
- 字数与格式。

Writer 不看：

- rewards、penalties、`net_signal`；
- commitment；
- fragment obligation；
- detector 名称；
- repair 教程；
- “章节作用、阶段意义、人物成长”等规划术语；
- 自动 subtype 写法。

如果没有经确认的本书样本，就使用中性现代白话，不自动借用公版作家或类型模板。

---

## 4. 各角色的调用边界

### 4.1 什么时候用 Planner

只有以下情况启用：

- 用户要求大纲；
- 长篇当前章没有足够材料；
- 章节顺序出现因果问题；
- 世界信息进入突兀；
- 用户明确选择强规划写法。

Planner 输出给 Writer 的不是大纲原文，而是具体事实：

- 当前谁在什么地方；
- 已经发生了什么；
- 眼前哪件事需要处理；
- 哪些事实会互相影响；
- 哪条规则不能违反；
- 与上一章有什么必要连接。

允许缺项。不能为了填满写作包制造目标、期限或冲突。

### 4.2 什么时候用 canon

canon 只帮助定位旧章，不代替正文。

候选事实必须区分：

- 叙述确认的事实；
- 人物说法；
- 人物猜测；
- 临时状态；
- 可被后文推翻的解释。

只有人工确认或机械上高度明确的事实，才作为硬约束。其他内容只作为检索线索。

必须修正：

- 删除“最后一句自动等于章节变化”；
- 状态更新形成时间序列，不一律记 conflict；
- 按当前人物、地点、物件、承诺和近期性检索；
- 每条保留来源和原文窗口；
- 冲突时回读原文，不靠账本投票。

### 4.3 什么时候用 Editor

以下情况启用：

- 用户说“检查、编辑、为什么像 AI”；
- 连续章节出现明显断裂；
- 阶段结束需要回读；
- 字数达标但正文仍显空泛；
- 用户对一章不满意，却说不清原因。

Editor 第一遍只看：

- 原稿；
- 必要旧章；
- 已确认事实；
- 用户 taste marks。

它不看 detector、L0 或 `net_signal`。第一遍报告完成后，才把 detector 结果用于统计检测器是否命中。

Editor 可以回答“没有值得现在修改的问题”，不要求每次找满三条。

### 4.4 什么时候用 Revision Writer

只有用户选择了具体问题，或明确授权修改时启用。

输入：

- 原文；
- 必要上下文；
- 一个具体问题；
- 本书认可片段；
- 用户要求。

输出：

- 原文保留；
- 候选 A；
- 必要时候选 B；
- 每个候选改变了什么。

用户选择后才 patch。

“去掉 AI 味”不是足够的修订指令。必须落到具体问题，例如：

- 重复解释；
- 抽象情绪；
- 对称总结；
- 主题升华；
- 模板化章末；
- 泛化对白；
- 连续钩子堆叠。

若问题遍布整章，应重写，不逐岛修改。

## 5. 作品声口

### 5.1 正例优先级

1. 用户明确认可的本书原文；
2. 独立 Editor 标为“应保留”且用户未反对的片段；
3. 用户主动提供的参考；
4. 用户主动选择的公版样本；
5. 中性 voice。

未经认可的首稿不能自动晋升为正例，否则会把第一章的 AI 腔固化。

### 5.2 正例怎样使用

- 每次只取少量与当前场景相关的片段；
- 样本用于叙述距离、密度和语言关系，不要求句式相似；
- 不计算 exemplar alignment；
- 不因连续章节“风格一致”而反复注入同一段；
- 用户可以撤销正例。

### 5.3 负例怎样使用

用户标记“太 AI”时，保存：

- 原文；
- 用户原因；
- 适用范围；
- 对应的认可片段。

普通 Writer 以正例为主，只在当前场景确实相关时收到一句具体提醒。完整负例主要供 Editor 和 Revision Writer 对照，避免坏句再次成为语言吸引子。

### 5.4 没有正例时

开篇或关键场景可以生成两个独立候选，由用户选择。没有用户选择时，不自动把任一候选设为作品声口。

这比平台替用户决定“像鲁迅”或“像网文”更可靠，但不应成为每章固定工序。

---

## 6. AI 味的处理

先从真实文本判断问题属于哪一层。

### 词句

例如对称句、总结词、空洞形容词、通用比喻。适合局部 Revision。

### 段落

例如先动作后解释、每段末尾升华、对白轮流递送信息。通常需要重写整段。

### 场景

例如人物只为说明世界、冲突靠误会拖延、所有细节都承担钩子。应回到场景或章段，不做句子修补。

### 章节结构

例如固定“异常—调查—反转—更大秘密”，每章作用过于整齐。应改规划方式。

### 基础模型

若当前模型稳定出现相同总结、对称和解释倾向，允许切换更适合中文叙事的模型。编排不能无限抵消基础模型分布。

任何修订都必须引用当前正文中的具体问题，不对抽象的“AI 味”直接下补丁。

---

## 7. repair 的边界

### 可自动

- 工具造成的重复段落；
- 破损引号；
- 明确错误的 Markdown 标题；
- 唯一定位失败后的安全停止；
- 文件写入造成的机械重复。

### 只能建议

- 碎拍；
- 连接词密集；
- 机构开头；
- 设定倾倒；
- 对称金句；
- 解释性总结；
- 模板化章末。

### 禁止岛修

- 人物选择不可信；
- 世界进入错误；
- 章节顺序无因果；
- 一章靠注水达到 3000；
- 全章声口错误；
- 本章不属于这本书。

detector 只提供候选证据，不能同时担任裁判和验收者。

---

## 8. 长度

默认目标仍为 3000—5000 个可见字符，用户点名优先。

低于目标时：

1. 判断本章材料是否足够；
2. 材料不足则改章段、改纲或保留短章；
3. 材料足够但跳写，则重写同一场；
4. 不 append 无关第二场；
5. 不把长度不足伪装成局部 repair span。

短章、间章和故意截断必须允许显式例外。

---

## 9. signals 与 legacy

默认路径：

- signals 只做 telemetry；
- Writer 不可见；
- 不控制交付；
- 不自动触发审美 patch；
- commitment 不做硬门；
- fragment 不生成写作义务。

`legacy` 只用于迁移期间回滚。新主链完成并通过工程回归后删除，不长期维护两套完整系统。

否则每次修改都要同时兼容 legacy / corrected，复杂度会重新增长。

---

## 10. 目标结构

迁移终态固定为：

```text
默认：用户 → 最小 Writer 上下文 → Writer → 落盘

规划：用户要求规划或材料不足 → Planner → 事实化写作包 → Writer

编辑：用户要求审读或阶段回读 → Blind Editor → 问题与证据

修订：用户选择问题 → Revision Writer → 候选 → 用户选择 → patch
```

持久状态固定为：

- manuscript：最终事实；
- outline：可修改计划；
- canon：带来源的事实与检索索引；
- taste / voice：用户确认的正例、负例原因和格式。

不再增加新的常驻评分层、承诺层或章节形状层。detector 留在遥测与 Editor 第二遍，不进入默认 Writer。

---

## 11. 迁移顺序

### 阶段 A：固定接口与回滚点

- 保存当前 corrected 的 system、Writer context 和工具 schema 快照；
- 为新主链保留短期 feature flag；
- 明确 writing pack、canon、voice、Editor report 和 Revision request 的数据边界；
- 不再扩展 legacy 功能。

### 阶段 B：完成最小 Writer 主链

修改：

- `writing/writing_pack.py`
- `writing/cards.py`
- `writing/subtype.py`
- `writing/focus.py`

目标：

- 不直传 spine 和 stage 抽象原文；
- 自动 subtype 不进入 Writer；
- 不统一要求“新章另起一场”；
- 只传必要事实和相关原文；
- 写作包允许缺项。

完成后，默认写章不调用 Planner、Editor 或 Revision；它们只从各自入口进入。

### 阶段 C：完成 canon 与相关原文检索

修改：

- `writing/canon.py`
- `writing/reread.py`
- `writing/focus.py`
- `tools/core/writing_tools.py`

目标：

- 删除末句 change 兜底；
- 区分事实、说法、猜测和状态；
- 状态按时间更新；
- 相关性检索替代前八条；
- 冲突回读原文；
- 未确认事实不做硬约束。

canon 输出分成两部分：

- 已确认事实：Writer 必须保持；
- 检索线索：只用于找到原文窗口，不直接约束正文。

### 阶段 D：建立作品 voice

修改：

- `writing/taste.py`
- `writing/cards.py`
- `writing/subtype.py`
- voice templates。

实现：

- 用户可确认、撤销本书正例；
- 未确认首稿不自动晋升；
- 自动 subtype 不进入 Writer；
- 普通 Writer 以少量正例为主；
- 负例原文只给 Editor / Revision Writer；
- 不计算 exemplar alignment。

作品尚无正例时使用中性 voice，不阻塞写作。

### 阶段 E：完成 Blind Editor

修改：

- `scenarios/writing/templates/editor.md`
- `writing/editor.py`
- editor phase 的 context 组装。

第一遍不注入 L0、`net_signal` 或 detector 名称。Editor 可以返回零个问题。detector 只在报告完成后附到遥测，不改写 Editor 结论。

### 阶段 F：完成授权 Revision

新增隔离 revision phase：

- 输入一个用户选择的问题、原文、必要上下文和本书正例；
- 返回原文与候选，不直接落盘；
- 用户选择后使用现有 patch 工具；
- 机械修复仍可自动；
- 整章问题返回 rewrite，不拆成多个岛。

### 阶段 G：统一长度与结构返回

- 3000—5000 为默认，用户点名优先；
- 长度不足先看场景容量；
- 材料不足返回 Planner / 改纲 / 保留短章；
- 材料足够返回同场 rewrite；
- 不 append 无关第二场；
- 事实冲突返回 Editor，不自动覆盖。

### 阶段 H：删除 legacy

新主链完成工程回归后：

- 删除 legacy 的评分回灌、commitment gate、范文轮换和审美 auto patch；
- 删除只服务 legacy 的分支与测试；
- 保留 telemetry 数据兼容所需的最小字段；
- `writing_architecture` 不再承担永久双轨。

每阶段运行：

```bash
bash scripts/preflight_unit.sh
```

## 12. 工程回归

测试用于确认目标结构确实工作，不决定采用哪种架构。

至少覆盖：

- 默认 Writer 看不到 spine、stage、subtype、signals、commitment 和 repair 教程；
- 写作包允许缺项，不自动补目标、冲突和期限；
- Planner、Editor、Revision 不会在普通写章时自动运行；
- canon 已确认事实与检索线索分开；
- canon 不再把末句自动记为 change；
- 状态更新不误判为不可覆盖冲突；
- 相关旧章按当前实体取回；
- 未确认首稿不能晋升 voice；
- Editor 第一遍看不到 detector；
- Editor 可以返回零个问题；
- Revision 不自动落盘；
- 用户选择后 patch 仍保留唯一定位、历史和授权；
- 低于 3000 不会 append 无关场次；
- legacy 删除后默认流程仍能选书、写纲、写章、编辑和修订。

## 13. 风险

- Writer 看得更少可能漏伏笔：允许主动回读，并记录遗漏。
- Planner 事实化可能删掉气氛和模糊动机：同时提供少量原文窗口。
- canon 会误提取：原文优先，未确认条目不做硬约束。
- 正例会固化坏声口：必须经用户或独立审读确认，可撤销。
- Revision Writer 可能只做同义改写：保留原文，候选盲选，不用 detector 消失作为成功。
- Editor 仍可能共享基础模型偏见：最终依赖用户或异模型对照。
- 多调用增加成本：Planner、Editor、Revision 都按需。
- 3000 字可能与作品冲突：允许显式短章。

---

## 14. 完成状态

迁移完成时，系统结构应满足：

- 普通写章只经过最小 Writer 主链；
- Planner 只负责规划和材料不足；
- canon 只提供已确认事实与原文定位；
- voice 只来自用户确认内容或中性默认；
- Editor 第一遍完全不受 detector 引导；
- Revision 必须有具体问题和用户授权；
- 机械修复与审美修订分开；
- 长度不足不触发无关扩写；
- legacy 已删除；
- system、voice、writing pack、Editor 和工具没有重复写作课。

小说质量层面期望：

- 后一章建立在前一章已经发生的变化上；
- 世界信息通过人物所受影响进入；
- 章节不靠抽象总结说明意义；
- 3000 字不靠重复心理、无效对白和临时冲突；
- 同一本书保持可辨认的语言关系，又不机械复制样本；
- 用户可以指出问题、选择修订，也可以保留有意的不规则。

最终原则：

> 默认路径保持最小；规划解决结构，事实解决连续性，声口解决语言，编辑指出问题，修订只在授权后发生。
