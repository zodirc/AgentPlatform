## 0.1 产品结论（写作优先 · 2026-07-24）

典型用法：用户打开云端 Web（一个 IP）→ 长篇写作、持续改稿 → **必须持久化**。

| 持久化方案 | 是否必要 | 说明 |
|------------|----------|------|
| 文件放用户本地（伴侣/Runner） | **写作主路径不必要** | 安装摩擦、双真相、毁盘预期都不匹配「打开网页写小说」 |
| 文件放服务器（个人 Work） | **必要且足够** | 已有多租户世界根、会话可换书不断（见 23 / 27） |
| 提供下载 / 导出 | **已有** | Web：`GET /api/v1/admin/workspace/download?path=`（工作区树 / 预览 / 资料库含 seed）；Agent 工具 `export_document` 写 `exports/` 后亦可下载 |

**和竞品的差：**

- 不是 **Claude Code / Cursor**：那些要改的是**本机仓库**；你们当前主交付是**云端书稿**。  
- 也不是 **DeepSeek 纯聊天**：你们有真 Work、落盘、长文续写；只是工作区在服务器，用下载闭环「带走」，而不是用本地盘当编辑主存。

**何时才需要重新打开「本地 Runner / 像 Cursor」讨论？**  
仅当产品明确要做「在 Web 里改对方**本机或远端 git 仓库**」——那是另一条产品线，和写小说不是同一题；即便做，也不等于 Cursor（无 IDE，仍是浏览器遥控 + 可选执行面）。

**工程含义：** 继续加强云端 Work + [31](../topics/sandbox.md) FS 沙箱 + 导出/下载；本地执行面保持 **⏸**。

## 0. 先承认：这题没有「抄一个竞品」的捷径

| 产品形态 | 工作区在哪 | 工具/shell 在哪 | 我们像不像 |
|----------|------------|-----------------|------------|
| **Claude Code / Cursor** | 用户本机目录 | 用户本机进程 | **不像默认形态**：它们是客户端 Agent；毁盘风险主要在用户自己 |
| **DeepSeek 等 Web 聊天** | 基本无「真工作区」 | 无任意 shell / 无用户盘挂载 | **不像能力面**：我们有 Turn、工具、Work、写作落盘 |
| **本平台（现状）** | **服务器**上的 Work 根 | **云端 runtime**（可 bwrap） | Web 是遥控板；手在共享主机上 |

因此：

- 不能假装「放开 curl + 网页」= Claude Code；  
- 也不能假装「有聊天窗」= DeepSeek——我们多了**真实可写工作区与 exec**；  
- 若再引入「用户本机当工作区」，是**第三条产品轴**，复杂度介于二者之间，且要和现有云端多租户共存。

**本文曾展开「可插拔本地 Runner」供对比；在写作主路径下已收敛为 A（见 §0.1）。下列 B 仅作归档构想。**

**冻结口径：写作与默认 Agent = 云端 Work + [31](../topics/sandbox.md) FS 沙箱 + 下载/导出；不上本地盘当主存。**

## 1. 原则（硬约束 · 与 30/31 同构）

1. **不影响 Agent 交互逻辑**：不改 `AgentEngine` while、事件契约、审批门、Plan 相位、工具名/参数形状。  
2. **不影响交互速率**：服从 [13](../core/13-rate-redlines.md) R1–R5——不挡 `turn.accepted`、首 token 前不加模型、热路径毫秒级。  
3. **成熟思路**：控制面与执行面分离（已有 api / runtime）；换的是**工具落点**，不是第二套 Agent。

**否决（未想清就不要做）：**

| 否决项 | 原因 |
|--------|------|
| 浏览器 File System Access 当主工作区 | 无真 shell；能力残缺 |
| 热路径 LLM / 探测「用本地还是云」 | 伤 R2、逻辑分叉 |
| 本地模式专用审批/SSE/loop | 双倍交互逻辑 |
| 默认同步双写云盘+本地盘 | 一致性地狱 |
| 因要做本地而拆掉云端 bwrap | 默认用户仍在共享主机上 |

---

## 2. 方案一句话

> **冻内核；执行面可插拔。默认 = 云端沙箱 Work；可选 = 用户本机 Runner（Turn 前冻结落点）。**

```text
浏览器（交互不变）
    ↔ api 控制面（建 Turn、已受理、SSE、审批）
         → 模型流式（首 token 路径不变）
         → 工具调用时：
              · 默认：云 runtime + FS 沙箱（bwrap）+ 出网保留
              · 可选：已绑定且在线的本地 Runner（同一工具名 / 同一审批事件）
```

- **云端 bwrap 仍然有用**（见 §6）：护的是共享主机可写面与多租户串味，与「批不批准 curl」无关。  
- **本地 Runner 护不了云端用户**；也**替代不了**云端沙箱。

## 3. 对用户：如何使用（构想）

### 3.1 默认（零安装 · 应永远是主路径）

1. 打开 Web → 登录 → 聊天 / 写作 / 批工具。  
2. 文件在平台个人 Work；shell 在云端沙箱内。  
3. 用户说「curl 某外网」→ `run_command` + 批准 → **允许出网**（产品口径，见 31 / 21 Q11）。

### 3.2 可选本地（高级 · 显式风险）

1. 设置中下载/安装伴侣或 CLI，选定**一个**本机目录，完成绑定。  
2. 伴侣在线；Web 将某 Session/Work **绑到该 Runner**（**Turn 外**完成）。  
3. 之后仍在浏览器交互；工具落到本机目录。  
4. 解绑后下一轮起回到云端。

| 用户必须理解的风险文案（若做） | 说明 |
|------------------------------|------|
| 命令在你勾选的目录执行 | 可能修改/删除其中文件 |
| `rm` 类经批准后仍可能清空该项目 | 平台挡逃逸，不挡「根内愚蠢」 |
| 伴侣离线时工具会失败 | 不堵受理/首 token；不自动改走云端偷跑（避免两套盘静默分叉——策略待决，见 §8） |

## 4. 对我们：如何维护（构想）

| 层 | 维护对象 | 数量 |
|----|----------|------|
| 交互契约 | Session/Turn/审批/SSE/工具名 | **一套** |
| api | 鉴权、建 Turn、推送；多「Run 执行面指针」 | 小增量 |
| 云 runtime | loop + 工具 + **bwrap FS 沙箱** | **主维护** |
| 本地 Runner | 薄适配：收工具调用 → 本机执行 → 回传 | 可选组件 |
| 证明 | `make gate` 仍只证明云端主路径 | Runner 另契约测 |

**改交互/速率 → 只动 api + 云 runtime。**  
**改「文件在谁盘上」→ 动绑定与 Runner。**  
禁止养第二套工作台或第二套状态机。

## 5. 能力与毁盘（必须写进产品认知）

| 问题 | 答案 |
|------|------|
| 会影响 Agent 能力吗？ | **默认云端：与现在同一工具面。** 本地模式是换落点，不是砍工具；本机缺运行时则个别命令失败。 |
| 会动对方主机目录吗？ | **会（仅绑本地时）。** 授权目录内，经批准的破坏性命令可以清空项目——与 Cursor 同类。 |
| `rm /*`？ | 本地隔离若只挂选中目录，应碰不到系统根；若用户把 `$HOME` 整盘绑上或隔离做砸，**可以毁大量本机数据**。 |
| 云端用户会被本机方案连坐吗？ | **不应。** 未绑定则永不碰用户笔记本。 |

---

## 6. 云端 bwrap 还要不要？

**要。** 在「默认工作区在服务器」成立期间，bwrap（或等价 OS FS 隔离）是共享主机的护栏：

- 挡跨 Work 写穿、cwd 伪装；  
- 出网默认开（批准 curl 可用）；  
- 与是否做本地 Runner **正交**。

详见 [31](../topics/sandbox.md)。**做本地 ≠ 可以拆云端沙箱。**

---

## 7. 为何「看起来简单、做起来不简单」（待你再想的点）

这些不是实现细节，是**产品与架构未决题**——拍板前不要开工：

1. **双真相**：书稿/代码以云端为准还是本机为准？换电脑、换浏览器怎么续？  
2. **离线策略**：Runner 掉线时，失败重试 / 拒绝 Turn / 临时回云（回云会不会写出第二份盘）？  
3. **写作主路径是否需要本地？** 写作强依赖云端种子/RAG/导出时，本地可能只对「Agent 改本机仓」有感。  
4. **安装与支持成本**：多 OS 伴侣、企业电脑策略、绑定令牌泄露。  
5. **安全边界文案**：Web 产品用户对「Agent 能删我盘」的预期远低于装了 Cursor 的开发者。  
6. **与多租户（27）关系**：云端仍要 Work ACL；本地是另一信任域，不能混进同一套「世界根」叙事而不加说明。  
7. **速率**：工具段本机慢/快可接受；若绑定握手或轮询进了受理路径，就违 R1——设计必须 Turn 前冻结。

## 8. 决策框架（已收敛）

| 选项 | 含义 | 建议 |
|------|------|------|
| **A. 只做云端** | Web + Work + bwrap；下载/导出带走 | **✅ 写作主路径采用** |
| **B. A + 可选本地 Runner** | 改本机目录 | ⏸ 仅当明确要做「Web 改本机/仓」再议；**不是写小说所需** |
| **C. 默认本地** | 打开即装伴侣 | ❌ |
| **D. 纯聊天、去掉 Work** | 接近 DeepSeek Web | ❌ 放弃已有差异化 |

**工程纪律：** 只迭代 A（含 31、导出体验）；B 不进主干，除非新产品线立项并开 ADR。

## 9. 若未来开做 B：最小切片（仍服从原则）

仅作备忘，**不是排期**：

1. 协议：Run 认领、工具调用下发、结果回流（复用现有事件类型，不新造审批语义）。

3. CLI 伴侣 MVP（单 OS 即可）。

5. 证明：云端 gate 全绿；Runner 契约单测；**禁止**用「本地 E2E」替换云端证明。

每步验收：**受理/首 token SLO 不劣化；golden 协议用例不因 B 改断言。**
